# 외부 API 중계: 비동기 전환 대신 Keep-Alive + 캐싱

## 배경

`sight-spring-backend`는 저사양 서버(ECS 기준 0.5 vCPU / 1GB 메모리)에서 동작한다. GitHub API 연동 등 외부 API를 중계하는 기능을 추가하기 전에, 외부 API 호출 시 Tomcat 워커 스레드가 blocking으로 묶이는 문제를 줄이기 위해 `RestTemplate` 대신 `WebClient` + Kotlin 코루틴(`suspend fun`)으로 전환하는 방안을 검토했다. 이 문서는 실제 벤치마크로 검증한 결과와 최종 결정을 기록한다.

## 검증 과정에서 발견한 것

Discord 도어락 알림 API(`/internal/door-lock/alert-die`)를 `suspend fun` + `WebClient`로 시범 전환하는 과정에서, **Spring Security의 커스텀 인증 필터가 비동기 재분배(ASYNC dispatch)에서 재실행되지 않아 401이 발생하는 문제**를 발견했다. `OncePerRequestFilter`는 기본적으로 `shouldNotFilterAsyncDispatch()`가 `true`라 ASYNC 재분배 시 필터를 건너뛰는데, `suspend fun` 컨트롤러는 처리 중 Tomcat 워커 스레드를 REQUEST 단계와 ASYNC 재분배 단계로 실제로 분리시킨다. 이 필터가 재실행되지 않으면 인증 정보가 사라진다.

이 문제는 `shouldNotFilterAsyncDispatch() = false`를 오버라이드해 해결했지만(`InternalApiAuthenticationFilter`, `CookieAuthenticationFilter`, `MockAuthenticationFilter`), **비동기 전환이 프레임워크 레벨의 예상 못한 함정을 동반한다**는 것을 보여주는 사례였다.

## 벤치마크 방법

개인 VM(4 vCPU / 7.7GB, 앱 컨테이너는 `--cpus=0.5 --memory=1g`로 프로덕션과 동일하게 제한)에 `main` 브랜치(동기)와 `WebClient` 전환 브랜치(비동기) 이미지를 각각 빌드해 배포하고, k6로 부하를 걸어 비교했다. 외부 API는 실제 GitHub/Discord 대신 지연시간을 재현하는 모의 서버로 대체해 조건을 통제했다.

## 결과

### 1. 가상의 큰 파일(1~10MB, 5~10초) 기준 — 비현실적 시나리오

| 동시 접속 | SYNC 성공률 | ASYNC 성공률 |
|---|---|---|
| 25~100명 | 실패 없음, 둘 다 비슷 | 실패 없음, 오히려 async가 스레드를 더 많이 씀 |
| 300명(과부하) | 54.0% | **77.7%** |

300명 과부하에서는 async가 확실히 우세했다. 다만 이는 실제 GitHub 파일 특성과 거리가 먼 가정(파일 하나에 5~10초)에서 나온 결과였다.

### 2. Keep-Alive(커넥션 풀) 적용 효과 — 300명 과부하 기준

`RestTemplate`(플레인) → Apache HttpClient5 기반 풀링으로, `WebClient`도 커넥션 풀을 16(기본값)에서 300으로 확장한 뒤 재측정했다.

| 설정 | 성공률 | 처리량(성공/초) |
|---|---|---|
| SYNC, 풀 없음 | 54.0% | ~4.8/s |
| **SYNC, keep-alive** | **65.2%** | ~5.1/s |
| ASYNC, 풀 없음 | 77.7% | ~8.6/s |
| ASYNC, keep-alive | 85.6% | ~11.6/s |

**과부하 상황에서 keep-alive는 SYNC만 적용해도 성공률이 11.2%p 개선됐다.** ASYNC 쪽 개선 폭이 더 컸던 건, 기본 커넥션 풀(16개)이 300 동시 요청 앞에서 병목이었기 때문으로 확인됐다.

### 3. 실측 GitHub 지연시간 반영 — 실제와 가장 가까운 조건

`raw.githubusercontent.com`에서 실제 파일 10개를 받아 측정: **평균 지연 296ms, 파일 크기 592B~4.1KB.** 앞서 가정했던 "5~10초, MB급 파일"과는 규모가 1,000배 이상 달랐다.

이 실측값(정규분포로 재현, 두 실행이 완전히 같은 트래픽을 받도록 시드 고정)과 **동아리 실사용 규모(최대 동시 50명)**를 기준으로 재검증한 결과:

| 설정 | 성공률 | 평균 지연 | p95 |
|---|---|---|---|
| SYNC, keep-alive 없음 | 100% | 343.76ms | 411.78ms |
| SYNC, keep-alive | 100% | 344.11ms | 409.53ms |
| ASYNC, keep-alive | 100% | 347.00ms | 413.33ms |

**세 설정이 사실상 동일했다.** 실사용 규모와 실제 파일 특성에서는 SYNC/ASYNC 차이는 물론, keep-alive 유무도 체감할 만한 차이가 없었다.

## 결정

### 1. Spring WebFlux(`WebClient`) + 코루틴 전면 전환은 하지 않는다

- 동아리 실사용 규모(동시 50명)와 실제 GitHub API 지연시간(평균 296ms, 수 KB) 조건에서는 비동기 전환의 성능 이득이 없다.
- 반면 비동기 전환은 인증 필터 재실행 문제 같은 프레임워크 레벨 함정을 동반하고, 컨트롤러부터 서비스·어댑터까지 호출 체인 전체를 `suspend`로 바꿔야 하며, 테스트 작성 방식도 새로 정립해야 한다.
- 비동기의 이점은 실사용 대비 6배(300명) 이상의 과부하 상황에서만 뚜렷하게 나타났다 — 지금 규모에는 맞지 않는 트레이드오프다.

### 2. HTTP Keep-Alive(커넥션 풀링)는 도입한다

- 과부하 상황에서 SYNC만 적용해도 성공률이 개선되는 걸 확인했다(54.0% → 65.2%).
- `RestTemplate`을 Apache HttpClient5 기반 풀링 팩토리로 교체하는 정도로 변경 범위가 작다.
- 실사용 규모에서는 손해가 없으므로, 향후 트래픽이 늘어날 때를 대비한 최소한의 조치로 도입한다.

### 3. GitHub·Discord 등 외부 API 값 조회에는 캐싱을 도입한다

- 실측 지연시간(평균 296ms)은 매 요청마다 반복되면 그대로 누적되는 비용이다. 캐싱을 적용하면 캐시 히트 시 이 비용을 수 ms 수준으로 줄일 수 있다.
- 실제로 예상되는 트래픽은 같은 시간에 같은 그룹원들이 같은 브랜치의 같은 파일 여러 번 조회하는 경우이다.
- 이번 벤치마크에서 keep-alive와 비동기 둘 다 이 규모에서는 뚜렷한 이득을 못 보여준 것과 달리, 캐싱은 반복 조회가 있는 한 확실한 개선을 기대할 수 있는 지점이다.

### 4. 깃허브 API 공용 토큰과 개인 토큰 사용자를 구분한다.

- 공용 토큰을 사용하면 깃허브 아이디가 없는 회원도 파일목록을 확인할 수 있다. 
- 공용 토큰을 사용하는 멤버는 시간당 요청 횟수를 백엔드에서 자체적으로 제한한다.
- 이 제한은 시간당 100회로 한다. 활동인원을 최대 50명으로 가정할 때 모든 사용자에게 시간당 100회를 할당하여도 깃허브의 제약인 시간당 5000회를 초과하지 않는다.
- 개인 토큰을 사용하면 깃허브 아이디를 연동하는 번거로움이 있지만 이러한 제한이 없다. 깃허브의 시간당 5000회 제약만 있다.
- 또한 개인 토큰을 사용하면 비공개 저장소에도 사용할 수 있다. 

## 참고

- 파일 중계 벤치마크에 쓰인 임시 컨트롤러(`BenchFileRelayController`)와 모의 파일 서버 스크립트는 검증 목적으로만 만들었으며 저장소에는 포함하지 않았다.
- Discord 웹훅 벤치마크에 쓰인 모의 서버·k6 스크립트는 `bench/`에 남겨뒀다.
- Discord 웹훅 전송 경로(`DoorLockAlertService`, `SupportRequestService`)는 이 저장소 히스토리에서 sync+keep-alive → async+keep-alive → async(풀링 제거) 순서로 실제 코드를 바꿔가며 벤치마크했고, 최종적으로는 **동기 + keep-alive** 상태로 되돌려 확정했다. 각 단계의 코드는 커밋으로 남아 있어 체크아웃해서 재현할 수 있다.
