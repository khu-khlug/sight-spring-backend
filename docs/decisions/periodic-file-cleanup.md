# 주기적 파일 청소의 판단 함수 등록

## 참조 유형별 판단 함수 등록

주기적 청소는 `file_reference`의 행을 읽어 저장된 `FileReferenceType`에 맞는 판단 함수를 호출한다. 같은 파일의 참조라도 활동보고 행이 사라지면 해제 대상이 되고, 삭제 표시만 된 기록의 참조는 복구를 위해 유지한다. 각 기능 서비스가 유형과 해제 조건을 함수에 함께 선언하면, 새 유형을 지원할 때 공통 청소기에 기능별 조회나 분기를 추가할 필요가 없다. 기록 첨부처럼 부가 행이 있는 기능도 같은 서비스에 해제 함수를 선언한다.

등록된 함수는 참조 한 건을 판단한다. 공통 청소기는 파일 행을 잠근 트랜잭션에서 부가 행과 공통 참조를 순서대로 정리하고, 마지막 참조가 없어졌을 때만 삭제 표시를 남긴다. R2 객체는 커밋 후 삭제한다. 아직 판단 함수가 등록되지 않은 유형은 참조를 보존한다. 링크 발급 후의 일회성 업로드 확인은 발급 서비스에서 예약한다.

## KSP 처리기를 별도 Gradle 모듈로 두는 이유

KSP는 Kotlin 소스를 빌드할 때 어노테이션을 읽는 도구다. 청소 판단 함수의 선언을 모아 서비스 메서드를 직접 연결하는 `GeneratedFileCleanupRegistry`를 생성한다. 함수 형식 오류, 같은 유형의 중복 등록, 판단 함수와 부가 행 해제 함수의 서비스 불일치를 빌드에서 발견할 수 있다. 청소가 실제 삭제로 이어지므로 등록 구성을 배포 전에 확인할 수 있다는 점이 중요하다.

메인 소스의 어노테이션을 읽으려면 KSP가 실행되기 전에 처리기를 컴파일해 로드할 수 있어야 한다. 처리기를 같은 메인 소스에 두면 메인 소스 처리에 필요한 코드가 그 처리 과정이 끝나야 컴파일되는 순환이 생긴다.

`build-tools/`는 빌드할 때 실행하는 도구를 두는 디렉터리다. 주기적 파일 청소의 등록 코드를 생성하는 Gradle 하위 프로젝트는 `build-tools/periodic-file-cleanup/`에 둔다. Gradle은 이 모듈을 먼저 빌드하고, 메인 프로젝트의 `ksp(project(":build-tools:periodic-file-cleanup"))`를 통해 처리기를 로드한다. 애플리케이션에는 생성된 등록부가 포함된다.

## 적용 범위와 재사용 기준

이 구조는 여러 기능의 참조를 한 작업에서 처리하고, 기능마다 다른 해제 판단을 등록하며, 잘못된 등록을 배포 전에 확인해야 하는 주기적 파일 청소에 한정한다. 일반 서비스의 의존성 연결에는 기존 Spring 생성자 주입 규칙을 적용한다.

다른 기능에서 같은 구조를 검토할 때는 등록 지점이 여러 기능에 걸쳐 분산되는지, 등록 오류를 빌드에서 잡는 가치가 있는지, 생성 코드와 Gradle 하위 모듈 및 Kotlin·KSP 버전 호환을 유지할 비용을 감수할 만한지 함께 판단한다.

실행 주기와 처리 순서는 [고아 파일 주기적 청소 설계](../plans/orphan-file-cleanup.md)를 따른다.
