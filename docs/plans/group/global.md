# 그룹 API 문서 공통 사항

그룹 API 및 구현 계획 문서에 공통으로 적용하는 사항을 정리한다.

## 문서 작성 기준

각 문서는 그룹이 소유한 리소스와 비즈니스 동작을 기준으로 작성한다. API의 권한, 상태 전이, 요청·응답, 저장 형식과 외부 시스템 계약을 설명한다.

- `새니타이징`에는 외부에서 들어온 값의 형식·허용값·위험 문자 검사 및 정제만 적는다.
- 응답 데이터 구성·직렬화·표시 형식, 저장 규칙, SQL 바인딩과 외부 요청 구성은 새니타이징에 포함하지 않고 해당 계약의 섹션에 적는다.
- 해당하는 외부 입력 검증·정제가 없으면 새니타이징 섹션을 만들지 않는다.

## Markdown·Tiptap 콘텐츠 처리

- Markdown·Tiptap 콘텐츠의 XSS 방지를 위한 새니타이징은 프런트엔드에서 표시할 때 수행한다. 렌더링 과정에서 스크립트·이벤트 핸들러·위험 URL이 실행되지 않도록 차단한다.
- 백엔드는 저장 시 입력 타입·길이와 Tiptap 문서 구조 등 API 계약을 검증하며, 화면 표시를 위한 새니타이징으로 원문을 변경하지 않는다.
- SQL 인젝션은 파라미터 바인딩으로 방지하며, 콘텐츠 새니타이징과 구분한다.

## 권한

그룹 권한 선언은 [그룹 권한 어노테이션](../group-auth.md)을 따른다. 기존 `Auth`와 `UserRole`은 유지한다. 그룹 권한이 필요한 API에는 `@Auth([UserRole.USER, UserRole.MANAGER])`와 `@GroupAuth`를 이 순서로 함께 명시한다. Auth의 사용자 역할 검사 후 GroupAuth의 그룹 제약을 검사하며 두 조건을 모두 만족해야 한다.

열람권한은 `VIEWER`다. 그룹원·그룹장·해당 그룹의 기록 작성자는 공개 범위와 관계없이 열람할 수 있으며, 비그룹원은 공개 범위로 판정한다. 비공개 그룹의 생성자도 그룹원이 아니면 열람할 수 없다.

### 그룹장이 없는 상태

- 운영 그룹의 마지막 그룹장이 탈퇴하면 `Group.leaderMemberId: Long?`와 DB의 `khlug_group.leader_member_id`를 null로 저장한다.
- 그룹장 아이디를 반환하는 조회 응답은 그룹장이 없으면 null을 반환한다. 멤버 목록의 `leaderUserId`도 같으며, 그룹원이 없으면 `members: []`다.
- 그룹장이 없으면 누구도 `GroupRole.LEADER`를 만족하지 않으며 요청자 그룹 역할도 `LEADER`로 반환하지 않는다. 운영진 예외 등 다른 권한은 별도로 판정한다.

## 아이디 타입

- 그룹·리스트·카드·기록·그룹 활동 로그의 식별자는 DB에서 `BIGINT`, 도메인에서 `Long`으로 유지하며 API의 JSON 요청·응답에서는 10진수 문자열로 전달한다. TSID를 JavaScript Number로 처리해 정밀도가 손실되지 않게 한다.
- 레거시 그룹·리스트·카드·기록·로그의 식별자 값과 참조를 그대로 유지한다. 이전 시 재채번하지 않으며 기존 URL이 가리키는 대상도 유지한다. Base32로 바꾸지 않고 10진수 표기를 사용하는 이유는 레거시 식별자와 URL의 호환성이다.
- 위 정수 식별자 문자열은 선행 0 없는 양의 Long의 10진수 표기다. 빈 값·0·음수·소수·Long 범위 초과·숫자가 아닌 값과 JSON 숫자 식별자는 400으로 거부한다. 경로·쿼리 값도 같은 정수 범위를 검사한다. 선택 필드의 생략·null 허용 여부는 각 계약을 따른다.
- 다른 리소스를 가리키는 참조 필드는 대상 리소스의 API 표현을 따른다. 회원 식별자는 기존 숫자(Long)를 유지하며 파일 업로드·활동보고·세미나는 기존 문자열 식별자를 유지한다. 수량과 모든 Long 값을 일괄 문자열화하지 않는다.

| 대상 | 도메인 선언 | API 타입 |
| :-- | :-- | :-- |
| 그룹 (`groupId`, 그룹 정보의 `id`) | `Group.id: Long` | 문자열(10진수 Long) |
| 회원 (`userId`, `leaderUserId`, `assigneeUserId` 등) | `Member.id: Long` | 숫자(Long) |
| 그룹 활동 로그 (`logs.id`) | `GroupLog.id: Long` | 문자열(10진수 Long) |
| 활동보고 (`reportId`) | `GroupActivityReport.id: String` | 문자열 |
| 세미나 (`seminarId`) | `BigSeminar.id: String` | 문자열 |
| 파일 업로드 (`fileUploadId`) | `FileUpload.id: String` | 문자열 |
| 기록 (`recordId`, 기록 필드의 `id`) | `GroupRecord.id: Long` | 문자열(10진수 Long) |
| 리스트 (`listId`, `targetListId`, `insertBeforeListId` 등) | `GroupList.id: Long` | 문자열(10진수 Long) |
| 카드 (`cardId`, `targetCardId`, `sourceCardId`, `insertBeforeCardId` 등) | `GroupCard.id: Long` | 문자열(10진수 Long) |

도메인 추가·변경 시 이 표와 관련 명세의 필드 타입을 함께 갱신한다.

## 신규 정수 식별자 발급

- 이 계약은 그룹 시스템 구현에 우선 적용한다. 일정·매칭·내부 연동 등 기존 API 전반의 채번·표현 전환은 [별도 TODO](../../../../tasks/open/existing-integer-id-migration-backend.md)로 관리한다. 같은 그룹·로그 테이블의 TSID를 기존 API가 읽는 경우에는 그 응답과 소비자도 함께 전환해야 하며, 대응 전에는 해당 대상의 TSID 쓰기를 활성화하지 않는다.
- 신규 그룹·리스트·카드·기록·그룹 활동 로그의 ID는 공통 `IntegerIdService.nextId()`로 발급한 TSID를 사용한다. 서비스에서 발급해 도메인 생성자에 Long으로 전달하고, 응답 경계에서 10진수 문자열로 변환한다.
- 서비스별 시간·랜덤 조합, 레거시 전역 sequence 테이블, 위 대상의 DB 자동 증가로 새 ID를 발급하지 않는다. 도메인은 발급 라이브러리·현재 시각·난수를 직접 호출하지 않는다.
- 같은 JVM은 생성기 하나를 공유한다. 배포 시 `INTEGER_ID_ENABLED=true`, JVM별로 고유한 `INTEGER_ID_NODE_ID`(0~1023), 운영에서 확인한 `INTEGER_ID_LEGACY_MAX_ID`를 설정한다. 중복 노드 번호를 실행하지 않으며 DB 임대·예약 테이블은 사용하지 않는다.
- 기존 데이터는 이전 SQL에서 원래 ID로 넣는다. 기존 ID 범위 검사, 노드 번호 재사용, 배포 환경 변수 설정과 전환 순서는 [TSID 결정·도입 계획](../../decisions/integer-id-tsid.md)을 따른다.
- 이 절은 구현할 공통 계약이다. 현재 공통 발급기만 추가된 단계이며 실제 생성 서비스 연결·사전 할당 저장·문자열 API·프런트 처리는 같은 백엔드 전환 배포에 맞춰 적용한다.

## 설명과 정렬 값의 저장 타입

- 그룹·리스트·카드 설명은 기존 데이터를 보존하도록 DB에서 `LONGTEXT`로 저장한다. 신규·수정 요청의 기존 입력 제한은 백엔드에서 적용하며 저장 타입 변경으로 완화하지 않는다.
- 리스트·카드 순서 값은 DB `BIGINT`, 도메인 `Long`으로 저장한다. 기존 순서와 식별자를 유지하며 순서 변경 API의 삽입 위치 계약은 유지한다.
- 그룹 관심 분야 컬럼은 레거시와 같은 `VARCHAR(1023)` 크기를 유지한다. 기존 `|` 구분 값은 이전 SQL에서 대응하는 enum 이름의 쉼표 구분 형식으로 변환하며 null과 빈 목록을 구분한다. 신규 요청의 허용 enum·중복 제한은 유지한다.

## 경험치

경험치 수치와 지급·차감 대상은 사용자 제공 회칙을 반영한 [경험치 기준](../experience-points.md)을 따른다. 실습 그룹은 더 이상 운영하지 않으므로 현행 설계에서 경험치 제외 예외를 적용하지 않는다.

## 활동에 따른 중단 상태 해제

- 중단 상태를 자동 해제하는 API는 각 문서의 `부수 효과 > 그룹 상태`에 그 동작을 명시한다. 활동 로그 기록이나 최근 활동 일시 갱신이라는 표현만으로 중단 해제를 추론하지 않는다.
- 현재 스프링 상태 `SUSPEND`는 명세의 `STOP`에 해당한다. 자동 해제는 이 상태를 `PROGRESS`로 바꾸며, 종료 상태를 자동으로 되돌리지 않는다.
- 자동 복귀 자체에 대한 경험치 변동이나 별도 재진행 로그는 추가하지 않는다. 원래 활동에 따른 경험치와 로그는 각 API 명세대로 처리한다.
- 참가·내보내기·나가기·그룹장 위임은 현재 스프링에 자동 해제가 구현돼 있다. 리스트·카드·기록의 활동에 따른 자동 해제는 해당 공통 사항과 개별 명세를 따른다.
- 활동보고 제출·수정·취소는 종료된 그룹에서는 할 수 없다. 중단 상태에서는 실행하며 진행 중으로 자동 전환한다.
- 채팅 등 부수 효과가 미정인 API에는 자동 해제를 임의로 적용하지 않는다.

### 중단 상태에서의 동작 제한

- 중단(`STOP`, 현재 스프링의 `SUSPEND`) 상태에서 그룹을 대상으로 하는 변경 동작은 중단을 해제하는 활동만 실행할 수 있다. 중단을 해제하지 않는 변경 동작은 거부한다.
- 활동에 따른 자동 해제는 개별 API의 `부수 효과 > 그룹 상태`에 명시한 경우에만 허용한다. 명시적인 재진행 API도 중단 상태에서 사용할 수 있다.
- 자동 해제 여부가 미정인 동작은 허용 대상으로 간주하지 않는다. 해당 API가 중단 상태에서 호출되면 실행 전에 `400 Bad Request`로 거부하고 데이터 변경·외부 호출·경험치·알림·로그 등 부수 효과를 발생시키지 않는다.
- 진행 중·종료 상태에서의 허용 여부는 각 API의 기존 조건을 따른다. 이 제한을 진행 중인 그룹만 허용한다는 뜻으로 확대하지 않는다.
- 특정 그룹을 대상으로 하지 않는 회원 전역 설정에는 그룹의 중단 상태 제한을 적용하지 않는다.
- 업로드 링크 발급은 그 파일을 제출하는 API(활동보고 제출·수정, 카드 커버 이미지 지정)가 중단 상태에서 실행되므로 중단 상태에서도 발급한다. 링크 발급 자체는 그룹 상태를 바꾸지 않으며, 중단 해제는 뒤따르는 제출 API가 한다.
- [기록 첨부 파일 업로드 완료](edit-window/group-record-files-uploaded.md)도 같은 이유로 중단 상태에서 실행하며 그룹 상태를 바꾸지 않는다. 업로드 링크를 받는 기록 작성·수정이 중단 상태에서 실행되기 때문이다.
- [기록 임시저장 저장](edit-window/group-record-draft-save.md)·[삭제](edit-window/group-record-draft-delete.md)도 중단 상태에서 실행하며 그룹 상태를 바꾸지 않는다. 임시저장은 중단 상태에서도 실행되는 기록 작성·수정의 작성 중 내용을 보존하는 것이고, 중단 해제는 뒤따르는 기록 작성·수정이 한다.

## 변경 API의 HTTP 메서드

- `PUT`: 변수에 값을 대입하듯 요청 바디의 값을 리소스나 하위 리소스에 그대로 저장하는 경우에 사용한다. 멱등성 필요.
- `PATCH`: 다음 경우에 사용한다.
  - 요청에서 생략한 필드는 기존 값을 유지하도록 동작하는 API
  - 멱등하지 않지만 `POST`의 의미가 맞지 않는 변경
  - 요청 바디의 값을 그대로 저장하지 않고, 함수처럼 요청 값으로부터 저장할 결과를 계산해내야 하는 변경 (예: 옮길 항목과 기준 항목으로부터 정렬된 순서를 계산하는 리스트·카드 순서 변경)

## 같은 값의 재요청

변경 API에 현재 값과 같은 값으로 다시 요청하면 성공으로 응답하되 경험치·알림·그룹 활동 로그·최근 활동 일시·중단 상태 해제 등 부수 효과를 반복하지 않는다. 개별 명세가 따로 정하면 개별 명세를 따른다.

## 파일 업로드와 삭제

활동보고·카드 커버·기록 첨부처럼 R2에 파일을 올리는 API는 아래 패턴과 흐름을 따른다. 주기적 정리는 [고아 파일 주기적 청소 설계](../orphan-file-cleanup.md)를 따른다.

기존 HTML의 파일·이미지는 [제공 결정](../../decisions/legacy-files.md)과 [파일 조회](../legacy-file-get.md)·[이미지 조회](../legacy-image-get.md)를 따른다. 레거시는 기존 `khlug_files`를 별도로 유지하며 테이블 접근·권한·청소 범위는 [제공 전환](../file-migration.md)을 따른다.

### 패턴

- 업로드 링크는 용도별 API로 발급한다. 공용 발급 API를 두지 않는다. 업로드 기록에 발급 경로를 저장해 제출 시 용도와 대상 리소스를 검증한다.
- 업로드 기록 하나는 R2 객체 하나와 1:1로 대응한다. DB가 파일의 상태를 결정하고, R2는 DB가 가리키는 객체를 보관만 한다.
- 파일 삭제는 업로드 기록에 삭제 표시를 먼저 남기고 R2 객체를 지운 뒤 업로드 기록을 지우는 순서로 처리한다.

### 업로드 흐름 (활동보고·카드 커버)

1. 링크 발급 API가 업로드 기록(파일 키, 발급자, 실제 아이디가 들어간 발급 경로, 미사용 상태)을 만들고 Presigned PUT URL을 반환한다. 이때 링크 만료 시각에 업로드 확인 여유 시간을 더한 시각으로 업로드 확인 예약을 등록한다.
2. 클라이언트가 URL로 R2에 직접 업로드한다.
3. 클라이언트가 `fileUploadId`를 제출 API에 보낸다.
4. 제출 API가 각 문서의 파일 검증 흐름(업로드 기록 존재, 발급 경로, 대상 리소스, 발급자, 미사용, 삭제 표시 없음, R2 객체 존재)을 통과시키고, 파일을 참조하는 데이터 저장과 사용 처리를 한 트랜잭션에서 처리한다.

기록 첨부 파일은 이 흐름 대신 아래 [기록 첨부 파일](#기록-첨부-파일)을 따른다.

### 기록 첨부 파일

기록 본문의 첨부 파일은 별도 업로드 링크 발급 API 없이 기록 작성·수정과 기록 임시저장 저장 요청 안에서 추가·참조·해제한다. 서버는 기록 본문을 파싱하지 않으며, 요청과 함께 받은 파일 식별자 배열과 서버에 저장된 연결 목록만 비교한다.

#### 기록 파일 식별자

- 본문의 파일 블록은 기록 파일 식별자와 백엔드 파일 아이디를 가지며 `src`·`href`에는 `/groups/{groupId}/files/{fileId}` 영구 주소를 저장한다. 기록 파일 식별자는 프런트가 정하며 한 기록 안에서만 유일하면 된다. 새 파일의 아이디를 받기 전에는 로컬 미리보기 상태로 두며 Presigned URL·로컬 blob URL을 저장 본문에 넣지 않는다.
- 기존 기록의 임시저장은 그 기록과 같은 식별자 공간을 쓴다.

#### 연결 목록

- 서버는 "소유자 + 기록 파일 식별자 → 업로드 기록" 연결을 행으로 저장한다. 소유자는 기록 또는 회원의 임시저장이다.
- 기록 첨부 파일의 업로드 기록은 연결 행이 하나 이상 있으면 사용 중이다. 같은 그룹의 여러 기록·임시저장이 한 파일을 함께 참조할 수 있다.
- 업로드 기록에는 R2 업로드가 끝났음을 확인한 업로드 완료 표시(`isUploaded`)를 둔다.
- 서버에 저장된 연결 목록이 그 기록(임시저장)의 첨부 파일 기준이다. 본문과 연결 목록은 서로 다를 수 있으며 서버는 이를 확인하지 않는다.

#### 요청의 파일 식별자 배열

기록 작성·수정과 임시저장 저장 요청은 본문과 함께 아래 배열을 보낸다.

| 이름 | 타입 | 설명 |
| :-- | :--: | :-- |
| `files` | 객체 배열 | 이 본문이 참조하는 파일 전체. 빈 배열이면 첨부 파일 없음 |
| `files.id` | 문자열 | 필수. 기록 파일 식별자. 배열 안에서 중복 불가 |
| `files.fileId` | 문자열 \| null | 필수. 백엔드 파일 아이디. 새 파일이면 null |
| `files.name` | 문자열 | `fileId`가 null이면 필수. 원본 파일명 |
| `files.size` | 숫자(uint) | `fileId`가 null이면 필수. 바이트 크기. [업로드 링크 기준](#업로드-링크-기준)의 최대 크기 이하 |
| `files.contentType` | 문자열 | `fileId`가 null이면 필수. MIME 타입 |

기록당 첨부 파일 개수는 제한하지 않는다. 파일 블록이 늘어나면 본문 크기 제한(1 MiB)에 걸리므로 그 제한이 사실상의 상한이다.

#### 허용 형식

본문에서 이미지·오디오·동영상 블록으로 표시하는 파일은 아래 MIME 타입으로 제한한다. 그 밖의 형식은 일반 파일 블록으로 첨부하며 형식을 제한하지 않는다. 서버는 본문을 파싱하지 않으므로 블록 종류와 형식의 대응은 클라이언트가 지키고, 서버는 아래 다운로드 전용 규칙으로 안전하게 내려준다.

| 블록 | 허용 MIME 타입 |
| :-- | :-- |
| 이미지 | `image/jpeg`, `image/png`, `image/webp`, `image/gif`, `image/avif` |
| 오디오 | `audio/mpeg`, `audio/mp4`, `audio/aac`, `audio/ogg`, `audio/wav`, `audio/flac`, `audio/webm` |
| 동영상 | `video/mp4`, `video/webm` |
| 파일 | 제한 없음 |

- `.mov`(`video/quicktime`)는 브라우저마다 재생 여부가 달라 동영상 블록이 아닌 일반 파일로 첨부한다.

#### 파일 제공 헤더

- Presigned GET URL에는 파일의 MIME 타입과 원본 파일명을 응답 헤더로 설정한다. 일반 파일은 `Content-Disposition: attachment`로 제공하며, 위 표의 이미지·오디오·동영상 형식은 인라인 응답을 허용한다.
- 스크립트 실행이 가능한 HTML·SVG·XHTML·JavaScript 등은 `Content-Disposition: attachment`로 제공해 브라우저의 직접 실행을 막는다. 본문 블록의 표시·재생과 첨부 목록의 다운로드 동작은 프런트에서 처리한다.
- 응답 헤더 설정이 다른 서명 URL은 같은 캐시로 섞지 않는다. 신규 그룹 파일과 레거시 파일·이미지 제공에 같은 기준을 적용한다.

#### 비교 규칙

요청 배열을 같은 소유자의 연결 목록과 비교해 한 트랜잭션에서 처리한다.

| 경우 | 처리 |
| :-- | :-- |
| `fileId`가 null | 업로드 기록·Presigned PUT URL·업로드 확인 예약을 만들고 연결 행을 추가한다. 응답 `uploads`에 담는다 |
| 같은 `id`와 같은 `fileId`의 연결이 이미 있음 | 그대로 둔다 |
| 같은 `id`의 연결이 있는데 `fileId`가 다름 | 400으로 거부한다. 파일을 바꾸려면 기존 식별자를 배열에서 빼고 새 식별자로 추가한다 |
| 새 `id`에 기존 `fileId` (같은 그룹의 다른 기록에서 가져온 파일) | 그 파일이 같은 그룹 파일인지 확인해 연결 행을 추가한다. 다른 그룹 파일이면 400으로 거부한다 |
| 새 `id`의 `fileId`가 존재하지 않거나 삭제 표시됨 | 400으로 거부한다. 업로드 확인 예약 등으로 정리된 파일을 가리키는 블록은 클라이언트가 지우고 다시 넣어야 한다 |
| 연결 목록에 있는데 배열에서 빠짐 | 연결 행을 지운다. 그 파일을 가리키는 연결 행이 하나도 남지 않으면 삭제 표시하고 커밋 후 [삭제 흐름](#삭제-흐름)을 적용한다 |

응답의 `uploads`는 아래 형식이며, 새 파일이 없으면 빈 배열이다. 클라이언트는 받은 `fileId`와 영구 주소 `url`을 해당 블록에 반영하고 `uploadUrl`로 파일을 올린다. 서버는 본문을 파싱하거나 치환하지 않는다. 최초 저장에 아이디 없는 블록이 포함되면 응답 반영 후 임시저장·수정으로 영구 주소를 저장한다. 파일이 모두 업로드돼 최종 저장이 완료될 때까지 이 후속 저장의 성공을 확인하고, 실패하면 본문을 유지해 재시도한다.

| 이름 | 타입 | 설명 |
| :-- | :--: | :-- |
| `uploads` | 객체 배열 | 새 파일의 업로드 정보 |
| `uploads.id` | 문자열 | 기록 파일 식별자 |
| `uploads.fileId` | 문자열 | 발급한 백엔드 파일 아이디 |
| `uploads.url` | 문자열 | 본문에 저장할 영구 주소 `/groups/{groupId}/files/{fileId}`. 업로드 완료 전에도 주소는 발급하며 파일 조회는 완료 전 404 |
| `uploads.uploadUrl` | 문자열 | Presigned PUT URL. 유효 시간은 [업로드 링크 기준](#업로드-링크-기준)을 따름 |

클라이언트는 업로드를 마친 파일을 [기록 첨부 파일 업로드 완료](edit-window/group-record-files-uploaded.md) API로 알린다. 서버는 파일을 검증해 업로드 완료 표시를 남긴다.

클라이언트가 업로드하지 않거나 실패해도 서버의 연결 목록은 바뀌지 않는다. 업로드 확인 예약이 업로드되지 않은 업로드 기록과 그 연결을 정리하며, 이후 그 블록은 404 미디어 블록으로 보인다.

#### 임시저장과 기록 저장 사이의 처리

- 임시저장은 회원당 하나이며, 소유 회원과 그룹·카드·수정 대상 기록(`recordId`, 새 기록이면 null)을 함께 저장한다. 회원이 같다는 이유만으로 최종 저장 시 임시저장을 삭제하지 않는다.
- 새 기록 작성 성공 시 삭제 대상은 요청자·요청 그룹·요청 카드가 일치하고 `recordId`가 null인 임시저장이다. 생성된 기록 아이디로 비교하지 않는다.
- 기록 수정 성공 시 삭제 대상은 요청자·요청 그룹·기록의 현재 소속 카드·요청 기록 아이디가 모두 일치하는 임시저장이다. 같은 카드의 새 기록 작성용 임시저장이나 다른 기록 수정용 임시저장은 대상이 아니다.
- 일치하는 임시저장이 없으면 기록 저장만 완료한다. 불일치하거나 다른 회원의 임시저장은 본문·대상·`updatedAt`·파일 연결을 유지한다. 유지되는 임시저장에만 연결된 파일도 삭제하지 않는다.
- 일치하는 경우 기록의 파일 연결을 먼저 생성·갱신한 뒤 해당 임시저장과 연결만 제거한다. 새 기록에 같은 `fileId`로 연결된 파일과 다른 기록·임시저장이 참조하는 파일은 유지하고, 연결 행이 하나도 남지 않은 파일만 삭제 흐름을 적용한다.
- 삭제 여부를 판정할 때 최신 임시저장의 소유자와 대상을 확인하고, 조건부 삭제와 파일 연결 해제를 기록 저장과 같은 트랜잭션에서 수행한다. 다른 탭이 임시저장을 다른 대상으로 대체했다면 이전에 읽어 둔 정보만으로 새 임시저장이나 그 파일 연결을 지우지 않는다.
- 임시저장 저장 API로 다른 그룹·카드·기록의 초안을 저장해 기존 임시저장을 대체하는 동작은 별개다. 이 경우 기존 임시저장의 연결은 모두 해제하며, 연결이 남지 않은 파일은 삭제 흐름을 따른다.

#### 조회 응답의 첨부 파일 목록

기록과 임시저장을 조회할 때 본문과 함께 연결 목록을 아래 배열로 반환한다. 본문은 저장된 영구 주소로 렌더링한다. 이 배열은 첨부 목록·업로드 상태를 표시해 사용자가 본문과의 일치를 확인하는 데 사용한다. 본문 렌더링은 파일 배열과 매핑하지 않고 저장된 영구 주소를 직접 사용한다. 별도의 첨부 목록 API는 두지 않는다. 단, [보관한 기록 목록 조회](archive/saved-records-get.md)는 미리보기 용도로 `files`를 반환하지 않으며 첨부 파일 연결 목록과 읽기 링크를 조회·발급하지 않는다.

| 이름 | 타입 | 설명 |
| :-- | :--: | :-- |
| `files` | 객체 배열 | 연결된 첨부 파일 전체 |
| `files.id` | 문자열 | 기록 파일 식별자 |
| `files.fileId` | 문자열 | 백엔드 파일 아이디 |
| `files.url` | 문자열 \| null | 영구 주소 `/groups/{groupId}/files/{fileId}`. 업로드 완료 표시가 없는 파일이면 null |
| `files.name` | 문자열 | 원본 파일명 |
| `files.size` | 숫자(uint) | 바이트 크기 |
| `files.contentType` | 문자열 | MIME 타입 |

- 조회 응답에서는 Presigned GET URL을 발급하지 않는다. 영구 주소 접근 시 [그룹 파일 조회](group-file-get.md)가 권한을 확인하고 파일별 `read_url`·`read_url_expires_at` 캐시를 사용해 302 리다이렉션한다.
- 레거시 메타데이터는 기존 `khlug_files`에 유지한다. 신규 업로드·그룹 파일 연결 테이블에 합치지 않으며 [제공 전환](../file-migration.md)을 따른다.
- 그룹 파일 경로는 그룹 열람 권한만 검사한다. 더 강한 권한이 필요한 파일은 이 경로로 제공하지 않고 각 기능 API에서 별도로 처리한다. 활동보고는 기존처럼 조회 API가 임시 읽기 주소를 직접 반환한다. 다른 Spring 서비스의 영구 파일 경로도 각 리소스의 권한 범위에 맞게 제공한다.

### 업로드 확인 예약

- 기존 `khlug_files`의 레거시 파일에는 신규 업로드 확인 예약을 적용하지 않는다.
- 예약 시각에 업로드 기록이 활동보고·카드 커버의 미사용 업로드이거나 업로드 완료 표시가 없는 기록 첨부 파일이고, 삭제 표시가 없으며 R2에 객체가 없으면 업로드되지 않은 것으로 본다. 기록 첨부 파일이면 연결 행도 함께 지운 뒤, 삭제 표시를 남기고 아래 삭제 흐름 2~4를 적용한다. R2 객체가 없으므로 삭제 결과는 `NoSuchKey`이며 업로드 기록을 지운다.
- 업로드 완료 표시가 없는 기록 첨부 파일이라도 R2에 객체가 있으면 업로드 완료 표시를 남긴다. 클라이언트가 업로드 후 완료 알림에 실패한 경우다.
- 예약 시각에 R2에 객체가 있으면 아무것도 하지 않는다. 업로드했지만 제출하지 않은 활동보고·카드 커버 파일은 주기적 청소가 정리한다.
- 예약이 서버 재시작 등으로 실행되지 않은 경우는 주기적 청소가 정리한다.

### 삭제 흐름

1. 한 트랜잭션에서 파일을 참조하던 데이터를 정리하고 해당 업로드 기록에 삭제 표시와 그 시각을 남긴다.
2. 트랜잭션 커밋 후 R2에서 객체를 삭제한다.
3. 삭제가 성공하거나 객체가 이미 없으면(`NoSuchKey`) 업로드 기록을 지운다.
4. 그 밖의 실패(권한 오류, `NoSuchBucket`, 5xx, 네트워크 오류)는 업로드 기록을 남겨 두고 주기적 청소에서 다시 시도한다.

### 지켜야 할 것

- R2 객체를 DB 트랜잭션 안에서 지우거나 DB 커밋 전에 지우지 않는다. DB 변경이 실패하면 DB가 없는 파일을 가리키게 된다.
- R2 삭제 결과로 사용자 요청의 성공·실패를 바꾸지 않는다. 사용자 요청은 1번 트랜잭션의 결과로 응답한다.
- `NoSuchKey`는 삭제 성공으로 처리한다. `NoSuchBucket`은 설정 오류이므로 성공으로 처리하지 않는다.
- 업로드 기록을 조회·검증하는 모든 곳은 삭제 표시가 없는 기록만 유효한 파일로 본다. 파일 검증 흐름에서 삭제 표시가 있으면 400으로 거부한다.
- 파일 교체(예: 커버 이미지 재지정)는 새 파일 연결과 기존 파일의 삭제 표시를 같은 트랜잭션에서 처리한 뒤 기존 파일에 삭제 흐름 2~4를 적용한다.

### 업로드 링크 기준

| 항목 | 값 |
| :-- | :-- |
| 업로드 링크(Presigned PUT URL) 유효 시간 | 발급 후 10분 |
| 업로드 확인 여유 시간 | 기본 1분. 링크 만료 직전에 시작한 업로드가 끝날 시간을 둔다. 큰 파일을 받는 API처럼 더 필요한 경우 개별 API 문서에서 따로 정한다 |
| 파일 하나의 최대 크기 | 20 MiB (20 × 1024 × 1024 = 20,971,520바이트). 정확히 같은 크기는 허용 |
| 읽기 링크(Presigned GET URL) 유효 시간 | 발급 후 7일 (R2 최대치) |
| 읽기 링크 재발급 기준 | 파일 접근 시 캐시가 없거나 만료까지 1분 이하이면 새로 발급. 영구 주소 자체는 만료되지 않음 |

### 파일 청소 기준

| 항목 | 값 |
| :-- | :-- |
| 청소 실행 시각 | 매월 1일 03:00 (KST) |
| 미사용 업로드 청소 대상 | 업로드 확인 예약 시각(링크 만료 시각 + 업로드 확인 여유 시간)이 지났는데도 미사용인 활동보고·카드 커버 업로드 기록, 연결 행이 하나도 없는 기록 첨부 업로드 기록 |

## 저장소 API

캐시 재검증, 사용자별 시간당 할당량과 단일 GitHub fetcher의 스케줄러는 [저장소 API 공통 사항](repo/global.md)을 따른다.

## 공통 실패 응답

아래는 각 API가 참조하는 기본 실패 응답이다. 같은 상황에 개별 명세가 별도 코드를 정하면 개별 명세를 따른다.

| 상황 | 응답 코드 |
| :-- | :--: |
| 인증되지 않음 | 401 |
| 요청에 필요한 열람·변경·작성자 권한이 없음 | 403 |
| 경로의 리소스가 없거나 경로로 지정한 그룹·카드 소속이 아님 | 404 |
| 요청의 필수 값·타입·허용 범위가 잘못됨 | 400 |
| 대상 카드·기록이 소프트 삭제됨 | 400 |

경로에 그룹·리스트·카드·기록이 함께 지정되면 실제 소속 관계를 검증한다. 다른 그룹의 리소스 아이디로 접근할 수 없다.

### 소프트 삭제된 카드·기록

- 삭제된 카드·기록을 대상으로 한 요청은 조회·변경 모두 `400`으로 응답한다. 경로의 기록이 속한 카드가 삭제된 경우와 요청 바디로 지정한 카드·기록이 삭제된 경우도 같다.
- 아이디에 해당하는 카드·기록이 아예 없거나 경로 그룹에 속하지 않으면 `404`다.
  - 아예 없음: 그 아이디로 만들어진 카드·기록이 없는 경우. 잘못된 아이디를 보내거나 주소에 임의의 아이디를 넣은 경우가 해당한다. 소프트 삭제된 카드·기록은 행이 남아 있으므로 여기에 해당하지 않는다.
  - 경로 그룹에 속하지 않음: 카드 `123`이 A 그룹에 있는데 `GET /groups/B/cards/123`으로 요청한 경우. 기록은 현재 소속 카드의 그룹으로 판단하므로, A 그룹 카드의 기록을 `/groups/B/records/:recordId`로 요청해도 `404`다. 다른 그룹 사용자에게 그 아이디가 존재하는지 드러내지 않는다.
- 경로가 특정 상태의 카드·기록만을 대상으로 하는 경우(예: `/groups/:groupId/deleted-cards/:cardId`는 삭제된 카드만 대상)에는 그 상태가 아닌 카드·기록은 해당 경로의 리소스가 아니므로 `404`다. 위의 `400` 규칙은 상태를 구분하지 않는 일반 경로(`/groups/:groupId/cards/:cardId`, `/groups/:groupId/records/:recordId`)에 적용한다.
- 삭제된 카드·기록을 다루도록 정해진 API(카드·기록 복구, 삭제된 카드 목록, 기록 목록의 `includeDeleted=true`, 개인 보관 해제)는 개별 명세를 따른다.

설계 결정:

- 카드·기록은 소프트 삭제되므로 삭제된 뒤에도 아이디로 찾을 수 있다. 리소스가 없는 것이 아니라 삭제된 대상을 다시 삭제·변경·조회하라는 요청 자체가 잘못된 입력이므로 `404`가 아닌 `400`으로 응답한다.

## 그룹 API 시각 표기: UTC

### 시각 표기 계약

- 그룹 관련 API의 요청·응답에서 시각 값은 UTC 기준 ISO 8601 문자열로 표기한다. 끝에 `Z` 접미사를 반드시 붙인다.
  - 예: 한국 시간 2026-10-22 오후 9시 → `"2026-10-22T12:00:00Z"`
- 오프셋이 없는 값(`"2026-10-22T21:00:00"`)이나 KST 오프셋 값(`"2026-10-22T21:00:00+09:00"`)은 쓰지 않는다.
- 날짜만 필요한 값은 시각으로 바꾸지 않고 `YYYY-MM-DD` 문자열로 표기한다.

### 설계 결정

API마다 시각 해석 기준이 달라지는 것을 피하기 위해 워크스페이스의 UTC 직렬화 기준을 그룹 API에도 적용한다.

- `sight-workspace/knowledge/backend/principles.md` "API 응답 직렬화": `Instant`는 ISO 8601 UTC 문자열로 직렬화된다.

### 레거시 `LocalDateTime` 컬럼

그룹 엔티티의 `createdAt`, `updatedAt`, `changedAt` 등은 시간대 정보가 없는 `LocalDateTime`이다. 이 값을 응답할 때는 저장 기준 시간대로 해석해 UTC 시점으로 변환한 뒤 표기해야 한다.
