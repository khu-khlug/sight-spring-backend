# 저장소 API 공통 사항

이 문서는 저장소 조회 API의 캐시 재검증, 공용 GitHub 토큰의 사용자별 할당량과 공통 GitHub fetcher의 호출 제어를 정의한다. 브랜치 목록·커밋 목록·파일 트리 조회는 GET과 쿼리 파라미터를 사용하며 요청 바디는 받지 않는다. GitHub에 보내는 외부 조회는 조건부 GET을 사용한다.

외부 요청의 입력·출력은 [GitHub API 목록](github-apis.md)을 참고한다.

## 쿼리 값 인코딩

- 저장소 URL과 브랜치명은 쿼리 파라미터 값으로 전달한다.
- 호출자는 원문 값을 HTTP 클라이언트의 쿼리 파라미터 기능에 전달해 한 번만 인코딩한다. 미리 인코딩한 값을 다시 인코딩하거나, URL을 문자열로 직접 이어 붙이지 않는다.
- 백엔드는 `@RequestParam`으로 받은 값을 원문 값으로 취급하며 추가 URL 디코딩을 하지 않는다. 원문 URL 안에 포함된 `%2F` 등의 이스케이프를 임의로 풀지 않는다.
- 백엔드가 저장소 서비스 API를 호출할 때는 해당 서비스의 경로·쿼리 형식에 맞게 원문 값을 별도로 인코딩한다. 수신 요청의 인코딩 문자열을 그대로 재사용하지 않는다.

## 캐시 갱신 쿼리

| 이름 | 타입 | 기본값 | 의미 |
| :-- | :--: | :--: | :-- |
| `refresh` | 불리언 | `false` | `true`이면 캐시 유효기간이 남아 있어도 GitHub에 조건부 GET으로 재검증함 |

- 브랜치 목록·커밋 목록·파일 트리 조회 API에 공통 적용한다. `refresh`는 각 API의 쿼리 파라미터로 받는다.
- 생략하거나 `false`이고 유효기간이 남은 캐시가 있으면 외부 호출 없이 반환한다. 캐시 유효기간이 지났거나 캐시가 없으면 공통 fetcher를 통해 조회한다.
- `true`이면 해당 요청 조건의 캐시를 즉시 재검증한다. 저장해 둔 본문과 검증자(`ETag` 등)를 먼저 삭제하지 않는다. 커밋 목록은 아래 브랜치 커밋 캐시 규칙에 따라 0페이지만 재검증하고, 변경이 확인되면 해당 브랜치의 전체 페이지를 초기화한다.
- `refresh`는 `true` 또는 `false`만 허용하며 그 외 값은 `400 Bad Request`로 거부한다.
- `refresh=true`도 각 API의 권한과 조건 및 사용자별 호출량 제한을 그대로 적용한다. GitHub의 시간당 기본 호출 한도를 실제로 소모한 경우에만 원인 사용자에게 차감한다.
- 같은 저장소의 `refresh=true` 요청은 1분에 최대 10번까지 처리한다. 사용자별 시간당 100회 한도와 별도로 적용한다. 1분 안에 10번을 넘는 요청은 GitHub를 호출하지 않고 `429 Too Many Requests`로 거부한다. 이 제한은 캐시 유효기간과 별개다.
- 별도의 `POST /groups/:groupId/repository/refresh` API는 제공하지 않는다.

## 조건부 GET과 캐시 재검증

- GitHub에 조회 요청을 보낼 때 저장된 검증자가 있으면 항상 조건부 GET을 사용한다. `ETag`가 있으면 원문 값을 `If-None-Match`로 보내고, `ETag`가 없고 `Last-Modified`가 있으면 `If-Modified-Since`로 보낸다.
- 최초 조회, 캐시가 제거된 경우 또는 GitHub가 검증자를 제공하지 않는 경우에는 보낼 검증자가 없으므로 일반 GET으로 조회한다. 임의의 검증자나 `If-None-Match: *`로 대체하지 않는다.
- 요청의 인증 정보는 계속 전송한다. 올바르게 인증한 조건부 GET의 `304 Not Modified`는 GitHub의 기본 시간당 호출 한도를 소모하지 않는다.
- 응답 본문과 검증자는 동일한 GitHub 요청 URL·쿼리·응답 형식·인증 범위별로 대응시켜 보관한다. 서로 다른 페이지나 사용자 권한 범위의 본문·검증자를 섞지 않는다.
- 캐시가 만료되었다는 이유만으로 본문과 검증자를 즉시 삭제하지 않는다. 만료는 외부 재검증이 필요한 시점이며 저장 데이터의 제거 시점과 구분한다.
- `304`이면 저장된 본문을 재사용하고 캐시 유효기간을 갱신한다. GitHub의 `304`를 응답 본문 없이 그대로 전달하지 않고 해당 조회 API의 정상 데이터 응답을 반환한다.
- `200`이면 새 응답 본문·검증자로 캐시를 교체하고 유효기간을 갱신한다. 기존 본문에 대한 검증자를 새 본문과 함께 재사용하지 않는다.
- 오류 응답을 성공한 재검증으로 취급하거나 기존 본문의 유효기간을 연장하지 않는다.

### 캐시 유효기간

| 캐시 | 유효기간 | 이유 |
| :-- | :-- | :-- |
| 브랜치 목록 | 10분 | 응답에 브랜치 끝 커밋을 담지 않으므로 브랜치 추가·삭제와 기본 브랜치 변경 때만 바뀐다. GitHub 원본 응답은 push마다 바뀌어 재검증이 `200`이 되기 쉬우므로 재검증 횟수를 줄인다 |
| 파일 트리 | 영구 (재검증하지 않음) | 커밋 SHA로 정해진 트리는 내용이 바뀌지 않는다. `refresh=true`여도 트리는 재검증하지 않으며, `branch`로 요청한 경우의 끝 커밋 결정은 브랜치 커밋 캐시를 따른다 |
| 브랜치 커밋 (브랜치 단위 전체) | 1분 | 새 커밋이 생기면 모든 페이지가 밀리므로 페이지별로 나누지 않고 브랜치 캐시 전체에 하나의 유효기간을 둔다. push마다 바뀌는 데이터라 짧게 두며, 재검증은 0페이지 조건부 GET 한 번이라 대부분 `304`로 끝난다 |

### 캐시 보관

- 캐시 테이블마다 최대 행 수를 두고, 넘으면 마지막으로 조회된 시각이 가장 오래된 행부터 덮어쓴다. 유효기간이 영구인 캐시도 이 방식으로만 정리된다.
- 행이 조회될 때마다 마지막 조회 시각을 갱신한다. 마지막으로 가져온 시각을 기준으로 지우면 자주 조회하는 영구 캐시가 먼저 밀려나므로 쓰지 않는다.
- 브랜치 목록·브랜치 커밋·파일 트리 캐시는 종류를 구분하지 않고 한 테이블에 보관하며, 최대 행 수는 1,000행이다. 활성 저장소 약 100개에 저장소당 자주 쓰는 행 약 10개(브랜치 목록 1, 브랜치 커밋 2~3, 파일 트리 5 안팎)를 기준으로 정한 값이다.

근거: [GitHub 조건부 요청 문서](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests).

## 브랜치 커밋 캐시

- 저장소·브랜치 및 인증 범위별로 캐시 행 하나를 두고, 확보한 커밋 페이지들을 MySQL `JSON` 타입 컬럼 하나에 저장한다. 모든 커밋을 영구 보관하는 테이블이 아니라 최근 요청으로 확보한 이력을 보관하는 캐시다. 보관과 제거는 [캐시 보관](#캐시-보관)을 따른다.
- `pages` 배열의 인덱스는 0부터 시작하는 `page`와 일치한다. 각 원소는 아래 타입 스키마의 페이지 객체이며, `commits`는 최대 30개다. `limit`·`skip` 옵션은 받지 않는다.
- 요청한 페이지가 유효한 캐시에 있으면 해당 페이지의 `commits`와 다음 페이지 존재 여부만 반환한다. 캐시에 여러 페이지가 있어도 `page=0` 요청에는 첫 페이지의 최대 30개만 반환한다. MySQL에서는 `JSON_EXTRACT(commit_cache, '$.pages[0]')`처럼 필요한 페이지 객체만 조회할 수 있다.
- `hasNext`는 GitHub 응답의 `Link` 헤더에 `rel="next"`가 있는지로 판단한다. 정확히 30개가 반환되었다는 이유만으로 다음 페이지가 있다고 판단하지 않는다. GitHub 커밋 목록 응답에는 전체 커밋 수가 없으며, 캐시에 확보한 개수를 전체 커밋 수로 간주하지 않는다.

### 유효기간과 재검증

- 유효기간은 페이지별로 두지 않고 브랜치 캐시 전체에 하나만 둔다. 새 커밋이 생기면 기존 커밋이 모두 뒤 페이지로 밀리므로 일부 페이지만 유효하다고 볼 수 없다. 값은 [캐시 유효기간](#캐시-유효기간)을 따른다.
- 유효기간이 지났거나 `refresh=true`이면 0페이지만 조건부 GET으로 재검증한다.
  - `304`이면 브랜치 끝 커밋이 그대로이므로 캐시 전체가 유효하다. 끝 커밋이 같으면 그 조상 이력 전체가 같기 때문이다. `validatedAt`만 갱신한다.
  - `200`이면 캐시 전체를 초기화하고 그 응답을 새 0페이지로 저장한다. 이전 페이지·검증자는 모두 폐기하며 이전 페이지와 새 페이지를 섞지 않는다. 검증자가 없어 일반 GET으로 가져온 경우도 같다.
- `etag`는 0페이지 응답 헤더의 원문만 보관하며, GitHub가 제공하지 않으면 `null`이다. 1페이지 이후는 재검증하지 않으므로 검증자를 보관하지 않는다.

### 다음 페이지 확보

- 아직 확보하지 않은 다음 페이지는 GitHub에서 브랜치 이름 대신 캐시의 끝 커밋 SHA(`headSha`)를 `sha`로 지정하고 `per_page=30`, `page=요청 page + 1`로 조회해 `pages`에 추가한다. 끝 커밋 SHA를 기준으로 조회하므로 그 사이 브랜치에 새 커밋이 생겨도 캐시된 페이지와 경계가 어긋나지 않는다.
- 다음 페이지 추가는 캐시의 변경으로 취급하지 않으며 `validatedAt`을 바꾸지 않는다.
- 인덱스가 밀리지 않도록 페이지를 건너뛰어 추가하지 않으며, 중복 SHA 제거 등으로 GitHub 페이지 경계나 순서를 재구성하지 않는다.
- 초기화 전에 시작한 추가 조회가 이전 이력의 페이지를 새 캐시에 삽입하지 않도록 브랜치별 갱신을 동기화한다. 추가 조회에 쓴 `headSha`가 현재 캐시의 `headSha`와 다르면 그 결과를 버린다.
- 브랜치의 전체 조상 이력을 대상으로 하며 분기 기준 브랜치 추정이나 분기점에서의 중단은 수행하지 않는다.

### 저장 타입 스키마

아래 타입은 MySQL JSON 컬럼의 저장 구조이며 API 응답 전체를 의미하지 않는다.

```typescript
type Commit = {
  sha: string;
  message: string;
  treeSha: string; // 해당 커밋의 루트 트리 SHA. 브랜치로 파일 트리를 조회할 때 사용
};

type CommitPage = {
  hasNext: boolean;
  commits: Commit[]; // 0~30개
};

type BranchCommitCache = {
  headSha: string; // 0페이지 첫 커밋 SHA = 브랜치 끝 커밋
  etag: string | null; // 0페이지 응답의 검증자
  validatedAt: string; // 0페이지 조회 또는 재검증이 성공한 UTC 시각 (ISO 8601)
  pages: CommitPage[]; // 배열 인덱스 = page
};
```

근거: [MySQL JSON 타입](https://dev.mysql.com/doc/refman/8.0/en/json.html), [JSON_EXTRACT](https://dev.mysql.com/doc/refman/8.0/en/json-search-functions.html#function_json-extract), [GitHub 커밋 목록](https://docs.github.com/en/rest/commits/commits#list-commits), [페이지네이션](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api#using-link-headers).

## 호출량 제한

- 공용 GitHub 토큰의 호출 가능량은 시간당 총 5,000회다.
- 사용자 한 명이 공용 토큰의 기본 호출 한도를 소모할 수 있는 횟수를 시간당 최대 100회로 제한한다.
- 한도는 원인 사용자의 회원 아이디를 기준으로 집계한다. 그룹·저장소·저장소 API 종류가 달라도 같은 사용자의 호출량을 합산한다.
- SIGHT API 요청 수나 모든 외부 전송 횟수가 아니라 GitHub의 기본 호출 한도를 실제로 소모한 횟수를 센다. 인증된 조건부 GET이 `304`를 반환하면 사용자 할당량을 차감하지 않는다.
- 외부 호출 전 원인 사용자의 남은 할당량을 확인하고 예상 차감량을 예약해 동시 요청으로 시간당 100회를 초과하지 않게 한다. 응답 후 실제 소모 여부에 따라 차감을 확정하며, `304`이거나 외부 호출을 전송하지 못했다면 예약을 해제한다.
- 실제 외부 호출이 필요하지만 해당 사용자의 할당량이 소진되었다면 GitHub에 요청하지 않고 `429 Too Many Requests`를 반환한다.
- 사용자별 잔여량이 남아 있어도 GitHub 공용 토큰의 전체 한도를 넘겨 호출할 수 없다. 전체 한도가 소진되어 외부 호출을 할 수 없으면 GitHub에 요청하지 않고 `502 Bad Gateway`를 반환한다.
- 사용자별 한도와 `refresh=true` 횟수 제한은 요청자가 SIGHT의 한도를 넘긴 경우이므로 `429`, 공용 토큰의 전체 한도 소진은 요청자와 무관한 서버 측 실패이므로 `502`로 구분한다.

## 차감 기준

| 상황 | 사용자 할당량 차감 |
| :-- | :-- |
| 캐시만으로 응답하고 GitHub API를 호출하지 않음 | 0회 |
| 인증된 조건부 GET이 `304`를 반환함 | 0회 |
| 일반 또는 조건부 GET이 `200`을 반환하고 GitHub 기본 호출 한도를 1회 소모함 | 1회 |
| 페이지 추가 조회 등으로 GitHub API를 여러 번 호출함 | 그중 GitHub 기본 호출 한도를 소모한 횟수만큼 |
| GitHub API에 재시도 요청을 전송함 | 각 재시도의 실제 기본 호출 한도 소모 여부에 따라 차감 |
| 오류 응답 또는 응답 대기 실패가 발생함 | GitHub 기본 호출 한도를 소모한 경우에만 차감. 전송 횟수만으로 차감을 확정하지 않음 |
| 권한·입력·할당량 검사 등으로 GitHub에 요청을 전송하지 않음 | 0회 |
| 캐시 만료 또는 `refresh=true`로 재검증함 | 동일한 기준. `304`이면 0회, 기본 호출 한도를 소모하면 해당 원인 사용자에게 차감 |

요청 한 건에서 여러 번 GitHub를 호출하면 각각의 호출 전에 남은 할당량을 확인한다. 중간에 소진되면 추가 외부 호출을 중단하고 `429 Too Many Requests`를 반환한다. 이미 GitHub 기본 한도를 소모해 차감이 확정된 횟수는 되돌리지 않는다.

GitHub의 기본 호출 한도와 보조 호출 제한은 별개다. `304`로 사용자 할당량을 차감하지 않는 요청도 공통 fetcher의 동시 요청 수·초당 호출 수 제한을 반드시 적용한다.

## 공통 GitHub fetcher와 스케줄러

- 백엔드는 GitHub HTTP 요청을 수행하는 단일 공통 fetcher를 둔다. 각 저장소 API는 fetcher에 요청을 전달하며 GitHub HTTP 요청을 직접 보내지 않는다.
- 요청에는 원인 사용자의 회원 아이디, 인증 범위와 조회 조건을 함께 전달한다. 캐시 만료 조회·강제 갱신·추가 페이지·재시도 모두 같은 fetcher를 거친다.
- fetcher 내부의 스케줄러가 대기 요청을 관리하고, 실행 중인 동시 요청 수와 초당 시작할 수 있는 호출 수를 각각 제한해 전송한다. API별 또는 사용자별로 독립된 제한기를 만들어 공용 토큰의 전체 제한을 우회하지 않는다.
- 동시 요청 수와 초당 호출 수의 운영 상한은 설정 가능하게 한다. GitHub의 동시 요청 제한과 분당 포인트 등 보조 제한 안에서 처리하도록 운영값을 정한다. 기본 운영값은 동시 요청 10개, 초당 호출 5회(분당 300회)다. GitHub 보조 한도(동시 요청 100개, REST 분당 900포인트)보다 낮게 두며, `304`도 보조 한도 포인트를 소모한다고 보고 정한 값이다.
- 동시에 들어온 동일한 조회 조건·인증 범위의 요청은 가능한 경우 하나의 외부 재검증으로 합쳐 불필요한 중복 호출을 줄인다. 차감은 실제 외부 요청을 유발한 원인 사용자 한 명에게만 귀속하고 기다리는 다른 사용자에게 중복 차감하지 않는다.
- `Retry-After`, 기본 한도 잔여량·초기화 시각, `403`·`429` 응답을 반영해 대기·재시도한다. 재시도도 스케줄러를 통과하며 즉시 재시도로 제한을 우회하지 않는다.
- 전체 잔여량은 GitHub 응답 헤더를 기준으로 관리하되, 전후 응답의 전역 잔여량 차이를 특정 사용자의 사용량으로 그대로 계산하지 않는다. 동시 호출이나 다른 호출의 소모가 섞일 수 있으므로 요청별 소모 규칙과 결과로 사용자 차감을 확정한다.
- 백엔드를 여러 인스턴스로 실행해도 공용 토큰을 사용하는 호출 전체에 제한이 적용되어야 한다. 인스턴스마다 각각 최대치까지 호출하게 두지 않고 공통 실행 경로나 공유 제한 상태를 사용한다.

근거: [GitHub 보조 호출 제한](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#about-secondary-rate-limits), [호출 제한 응답 처리](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit).

## 설계 결정

- 최근 요청된 커밋만 캐싱하므로 커밋별 영구 행으로 분리하지 않고 브랜치당 JSON 하나로 관리한다. MySQL JSON의 배열 인덱스 조회를 이용하면 전체 JSON을 애플리케이션으로 가져오지 않고 요청 페이지를 추출할 수 있다.
- 커밋을 GitHub 페이지와 같은 30개 단위로 묶어 저장해 GitHub 페이지와 저장 데이터의 대응 관계를 유지한다.
- 브랜치 끝 커밋이 같으면 조상 이력 전체가 같으므로, 0페이지 하나의 조건부 GET으로 브랜치 캐시 전체의 유효성을 판단한다. 페이지별로 재검증하지 않아 외부 호출을 줄인다.
- 커밋 추가·강제 push·리베이스로 페이지 경계가 이동했을 때 기존 페이지와 새 페이지가 섞이는 것을 피하기 위해, 0페이지 변경이 확인되면 전체 캐시를 초기화한다. 이전 이력과의 부분 병합이나 연속성 복구는 수행하지 않는다.
- 다음 페이지를 브랜치 이름이 아닌 캐시의 끝 커밋 SHA로 조회해, 캐시를 유지하는 동안 브랜치에 새 커밋이 생겨도 페이지 경계가 어긋나지 않게 한다.
- 별도 캐시 무효화와 후속 조회로 나누면 실제 외부 호출의 원인 사용자가 달라질 수 있으므로, 재검증과 조회를 한 요청에서 처리한다.
- 사용자별로 100회씩 할당하면 `5,000 ÷ 100 = 50`이므로 공용 토큰 한도를 최소 50명의 시간당 할당량으로 나눌 수 있다.
- 유효한 캐시 응답과 인증된 조건부 GET의 `304`는 공용 토큰의 기본 호출 한도를 소모하지 않으므로 사용자 할당량을 차감하지 않는다.
- 요청 한 건에 필요한 GitHub 호출 수와 결과가 다르므로 실제 GitHub 기본 호출 한도 소모에 맞춰 사용자 할당량을 차감한다.
- 단일 fetcher의 스케줄러에서 외부 호출을 제어해 사용자별 100회 제한만으로 방지할 수 없는 순간적인 동시 호출과 단시간 집중 호출을 제한한다.
- 다른 그룹이나 저장소를 요청해 사용자 한도를 우회하는 것을 막기 위해 회원 아이디 단위로 호출량을 합산한다.
