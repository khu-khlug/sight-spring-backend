# 그룹 저장소 브랜치 목록 조회

요청한 저장소의 브랜치 목록을 조회합니다. 외부 저장소 서비스(GitHub 등) 호출과 인증, 캐시는 백엔드가 담당합니다.

공용 GitHub 토큰의 사용자별 호출량은 [저장소 API 공통 사항](global.md)을 따릅니다.

## 운영 그룹인 경우

(해당 없음)

## API 경로

```
GET /groups/:groupId/repository/branches
```

## 권한

USER and 열람권한

## 조건

- `url`이 그룹에 등록된 저장소 URL(`repositoryUrls`) 중 하나여야 함

## 제한

- 브랜치는 최대 100개까지 반환한다. GitHub 브랜치 목록 API에 `per_page=100`, `page=1`로 한 번만 요청하고 다음 페이지는 가져오지 않는다. 이유는 [설계 결정](#설계-결정)을 따른다.

## 부수 효과

공용 토큰의 GitHub 기본 호출 한도를 실제로 소모한 경우에만 원인 사용자의 시간당 할당량을 차감함. 인증된 조건부 GET의 `304`는 차감하지 않음. 캐시 재검증과 공통 fetcher의 호출 제어는 [공통 사항](global.md)을 따름.

## 쿼리스트링

| 이름  |  타입  | 설명        |
| :---- | :----: | :---------- |
| `url` | 문자열 | 저장소 URL  |
| `refresh` | 불리언 | 생략 가능, 기본값 `false`. `true`이면 캐시 유효기간과 무관하게 조건부 GET으로 재검증. [공통 사항](global.md) 참고 |

## 요청 바디

(해당 없음)

## 성공 응답

```
200 OK
```

| 이름                 |   타입    | 설명                       |
| :------------------- | :-------: | :------------------------- |
| `branches`           | 객체 배열 | 브랜치 목록                |
| `branches.name`      |  문자열   | 브랜치 이름                |
| `branches.isDefault` |  불리언   | 저장소 기본 브랜치 여부    |

## 실패 응답

| 상황                                           | 응답 코드 |
| :--------------------------------------------- | :-------: |
| `url`이 그룹에 등록된 저장소가 아님            |    400    |
| 저장소 서비스에서 저장소를 찾을 수 없거나 접근할 수 없음 |    404    |
| 저장소 서비스 응답이 실패함 |    502    |
| 실제 GitHub 호출이 필요하지만 원인 사용자의 시간당 100회 할당량이 소진됨 | 429 |
| GitHub 공용 토큰의 전체 한도가 소진됨 | 502 |
| `refresh`가 `true`·`false`가 아님 | 400 |
| 같은 저장소에 1분 안에 `refresh=true`를 10번 넘게 요청함 | 429 |

## 설계 결정

### 브랜치 최대 100개

- 100은 GitHub 브랜치 목록 API가 한 페이지에 돌려줄 수 있는 최대 개수(`per_page` 최대값)다. 이 범위 안이면 GitHub 호출 한 번으로 목록 전체를 받는다.
- 그룹 활동에 쓰는 저장소는 브랜치가 100개를 넘는 경우가 사실상 없다. 브랜치가 그보다 많은 경우는 그룹과 무관한 대형 프로젝트 저장소를 등록했을 때 정도다.
- 100개를 넘는 저장소까지 지원하려면 요청 한 번에 GitHub를 여러 번 호출해야 한다. 그러면 사용자 할당량을 더 소모하고, 커밋 목록처럼 페이지별 캐시·재검증 규칙도 따로 정해야 한다. 드문 경우를 위해 이 비용과 복잡도를 늘리지 않는다.

## 테스트 케이스

1. 열람 권한이 있는 회원은 등록된 저장소의 브랜치 목록을 조회할 수 있다
   - 200 응답과 함께 브랜치 이름과 기본 브랜치 여부를 반환한다. 끝 커밋은 반환하지 않는다
   - 등록된 저장소를 GitHub에서 찾을 수 없거나 접근할 수 없으면 404, 그 밖의 GitHub 실패는 502 에러를 반환한다
2. 브랜치는 최대 100개까지 반환한다
   - 100개면 모두, 101개 이상이면 GitHub 첫 페이지의 100개만 반환한다. `per_page=100`, `page=1`로 한 번만 요청한다
3. 캐시는 10분간 쓴다
   - 검증 후 10분 직전에는 캐시만 반환하고, 정확히 10분부터는 본문과 검증자를 남긴 채 재검증한다
   - `refresh=true`면 유효기간이 남아도 재검증한다. 200이면 본문과 검증자를 함께 바꿔 브랜치 추가·삭제와 기본 브랜치 변경을 반영한다
4. 사용자별 한도는 원인 사용자의 시간당 100회다
   - 그룹·저장소·API 종류가 달라도 합산한다. 동시 요청은 미리 예약해 100회를 넘지 않는다
   - 99회 쓴 사용자의 한 번은 허용하고, 100회를 쓴 뒤 외부 호출이 필요하면 GitHub에 보내지 않고 429 에러를 반환한다. 캐시만으로 응답할 수 있으면 200이다
5. 캐시 응답과 인증된 304는 사용자 한도를 차감하지 않는다
   - 200·오류·재시도는 GitHub 기본 한도를 실제로 소모한 횟수만 원인 사용자에게 차감하고, 보내지 않았거나 304인 예약은 해제한다
   - 동시 재검증을 하나로 합치면 실제 원인 사용자 한 명에게만 차감한다
6. 공용 토큰의 전체 한도가 소진되면 502다
   - 공용 사용량 4,999회에서 마지막 1회는 허용하고, 5,000회 뒤에는 GitHub에 보내지 않고 502 에러를 반환한다
7. 같은 저장소의 `refresh=true`는 1분에 10번까지다
   - 10번째까지 허용하고 11번째는 GitHub를 호출하지 않고 429 에러를 반환한다. 다른 저장소의 횟수와는 따로 센다
8. 모든 GitHub 호출은 공통 fetcher를 거친다
   - 동시 10개·초당 5회 제한을 여러 인스턴스가 함께 쓰며 304에도 적용한다. `Retry-After`·잔여량·초기화 시각과 403·429를 반영해 재시도한다
9. 조건부 GET으로 재검증한다
   - ETag가 있으면 `If-None-Match`, ETag 없이 Last-Modified만 있으면 `If-Modified-Since`를 보내고, 둘 다 없으면 일반 GET을 보낸다. 인증 정보는 항상 보낸다
   - 304면 저장한 본문으로 200 응답을 만들고 유효기간을 갱신한다. 오류는 캐시에 저장하지 않고 유효기간도 늘리지 않는다
10. 캐시는 1,000행까지 보관한다
    - 조회할 때마다 마지막 조회 시각을 갱신하고, 1,001번째 행이 들어오면 마지막 조회가 가장 오래된 행을 교체한다
11. 등록된 저장소와 올바른 쿼리만 처리한다
    - 등록되지 않은 `url`, 필수 값 누락, `true`·`false`가 아닌 `refresh`는 400 에러를 반환하고 GitHub를 호출하지 않는다
    - 원문 URL·브랜치명을 다시 디코딩하거나 이중 인코딩하지 않고, GitHub 요청 형식에 맞게 인코딩한다
12. 그룹 상태와 관계없이 조회할 수 있다
    - 중단·종료 그룹에서도 열람 권한이 있으면 200 응답을 반환한다
13. 공개 범위에 따라 조회할 수 있는 회원이 정해진다
    - 비공개는 그룹원, 운영진 공개는 운영진, 회원 공개는 교류 회원을 제외한 회원, 완전 공개는 모든 로그인 회원이 조회할 수 있다
    - 범위 밖 회원이면 403, 인증되지 않으면 401, 그룹이 없으면 404 에러를 반환하며 GitHub를 호출하지 않는다
14. 조건이 다른 캐시는 섞지 않는다
    - 다른 저장소·쿼리·응답 형식·인증 범위의 본문이나 검증자를 섞어 쓰지 않는다
