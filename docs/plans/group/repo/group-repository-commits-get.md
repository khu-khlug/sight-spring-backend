# 그룹 저장소 커밋 목록 조회

요청한 브랜치의 전체 커밋 이력을 최신 커밋부터 조회합니다. 다른 브랜치와 공유하는 조상 커밋과 병합 커밋도 포함됩니다.

공용 GitHub 토큰의 사용자별 호출량은 [저장소 API 공통 사항](global.md)을 따릅니다.

## 운영 그룹인 경우

(해당 없음)

## API 경로

```
GET /groups/:groupId/repository/commits
```

## 권한

USER and 열람권한

## 조건

- `url`이 그룹에 등록된 저장소 URL(`repositoryUrls`) 중 하나여야 함
- `branch`가 해당 저장소에 있는 브랜치여야 함

## 제한

- 한 번에 받는 커밋 수는 30개로 고정함. 남은 이력이 30개 미만이면 남은 개수만 반환하며, 추가 이력은 `page`를 1씩 늘려 다시 요청해야 함. 개수를 지정하는 옵션은 받지 않음
- 백엔드에 30개보다 많은 이력이 캐시되어 있어도 요청한 범위만 반환함
- 조회 시작 위치는 `page × 30`임. GitHub에는 `page + 1`, `per_page=30`으로 요청함

## 부수 효과

공용 토큰의 GitHub 기본 호출 한도를 실제로 소모한 경우에만 원인 사용자의 시간당 할당량을 차감함. 인증된 조건부 GET의 `304`는 차감하지 않음. 캐시 재검증과 공통 fetcher의 호출 제어는 [공통 사항](global.md)을 따름.

## 쿼리스트링

| 이름         |    타입    | 기본값                   | 설명                                  |
| :----------- | :--------: | :----------------------: | :------------------------------------ |
| `url` | 문자열 | 없음(필수) | 그룹에 등록된 저장소 URL. 쿼리 값 인코딩은 [공통 사항](global.md)을 따름 |
| `branch` | 문자열 | 없음(필수) | 커밋을 조회할 브랜치 이름. 쿼리 값 인코딩은 [공통 사항](global.md)을 따름 |
| `page`       | 숫자(uint) |            0             | 0부터 시작하는 페이지 번호. `0`은 첫 30개, `1`은 다음 30개 |
| `refresh` | 불리언 | `false` | `true`이면 캐시 유효기간과 무관하게 조건부 GET으로 재검증. [공통 사항](global.md) 참고 |

## 요청 바디

(해당 없음)

## 성공 응답

```
200 OK
```

| 이름                  |    타입    | 설명                                                       |
| :-------------------- | :--------: | :--------------------------------------------------------- |
| `page`                | 숫자(uint) | 반환한 페이지 번호 (요청의 `page`와 같음) |
| `receivedCount`       | 숫자(uint) | 받은 커밋 수 (`commits` 길이)                              |
| `hasMore`             |   불리언   | 이보다 이전 커밋이 더 있는지                               |
| `commits`             | 객체 배열  | 커밋 목록. 최신 커밋이 앞                                  |
| `commits.sha`         |   문자열   | 커밋 SHA                                                   |
| `commits.message`     |   문자열   | 커밋 메시지 전체. HTML로 해석하지 않는 일반 텍스트 |

## 실패 응답

| 상황                                           | 응답 코드 |
| :--------------------------------------------- | :-------: |
| `url`이 그룹에 등록된 저장소가 아님            |    400    |
| 쿼리 파라미터의 `url` 또는 `branch`가 없거나 비어 있음 | 400 |
| `branch`가 저장소에 없음     |    404    |
| `page`가 0 이상의 정수가 아님 | 400 |
| GitHub 공용 토큰의 전체 한도가 소진됐거나 저장소 서비스 응답이 실패함 |    502    |
| 실제 GitHub 호출이 필요하지만 원인 사용자의 시간당 100회 할당량이 소진됨 | 429 |
| `refresh`가 `true`·`false`가 아님 | 400 |
| 같은 저장소에 1분 안에 `refresh=true`를 10번 넘게 요청함 | 429 |

## 설계 결정

- 공통 조상과의 거리만으로는 최초 분기 방향을 확정할 수 없고 병합·리베이스로 추정 결과가 달라질 수 있다. 잘못 추정한 분기점에서 이력이 누락되는 것을 피하기 위해 전체 이력을 조회한다.
- 30개 고정 단위로만 조회하므로 임의의 건너뛸 개수보다 조회 단위를 직접 나타내는 `page`를 사용한다.
- 캐시가 누적될수록 같은 요청의 응답 크기가 커지는 것을 방지하기 위해 캐시 보관 범위와 응답 범위를 분리한다.

## 테스트 케이스

1. 열람 권한이 있는 회원은 브랜치의 커밋 목록을 조회할 수 있다
   - 등록된 저장소와 있는 브랜치를 보내면 200 응답과 함께 최신순 커밋을 최대 30개 반환한다. 공통 조상과 병합 커밋도 포함한다
   - 커밋 메시지는 줄바꿈·HTML 모양 문자열도 일반 텍스트 원문으로 반환하고, 캐시의 `treeSha` 같은 내부 필드는 노출하지 않는다
   - 없는 브랜치는 404, GitHub 실패는 502 에러를 반환한다. `url`·`branch`가 없거나 비었거나 `page`가 0 이상의 정수가 아니면 400이다
2. `page`로 30개씩 나눠 조회한다
   - `page`를 생략하면 0이다. 캐시에 여러 페이지가 있어도 요청한 페이지만 반환한다
   - 마지막 페이지가 30개 미만이면 남은 개수만 반환한다. 정확히 30개여도 `Link` 헤더에 다음 페이지가 없으면 `hasMore: false`다
3. 브랜치 캐시 전체에 1분 유효기간 하나를 둔다
   - 1분 직전에는 캐시만 반환하고, 정확히 1분부터나 `refresh=true`면 0페이지만 조건부 GET으로 재검증한다
   - 304면 모든 페이지를 유지하고 `validatedAt`만 갱신한다. 200이면 이전 페이지와 검증자를 모두 버리고 새 0페이지로 초기화한다
4. 다음 페이지는 끝 커밋 SHA로 가져온다
   - 아직 없는 페이지는 캐시의 `headSha`를 `sha`로, `per_page=30`, `page=요청 page+1`로 조회해 붙인다. 페이지를 건너뛰거나 GitHub 페이지 경계를 재구성하지 않는다
   - 페이지를 붙여도 `validatedAt`은 바뀌지 않는다. 붙이는 도중 캐시가 초기화돼 `headSha`가 달라지면 그 결과를 버린다
5. 한 요청에서 여러 번 호출할 때도 한도를 확인한다
   - 호출이 두 번 필요한데 잔여량이 1회면 첫 호출만 보내고 429 에러를 반환한다. 이미 차감한 1회는 되돌리지 않는다
6. 사용자별 한도는 원인 사용자의 시간당 100회다
   - 그룹·저장소·API 종류가 달라도 합산한다. 동시 요청은 미리 예약해 100회를 넘지 않는다
   - 99회 쓴 사용자의 한 번은 허용하고, 100회를 쓴 뒤 외부 호출이 필요하면 GitHub에 보내지 않고 429 에러를 반환한다. 캐시만으로 응답할 수 있으면 200이다
7. 캐시 응답과 인증된 304는 사용자 한도를 차감하지 않는다
   - 200·오류·재시도는 GitHub 기본 한도를 실제로 소모한 횟수만 원인 사용자에게 차감하고, 보내지 않았거나 304인 예약은 해제한다
   - 동시 재검증을 하나로 합치면 실제 원인 사용자 한 명에게만 차감한다
8. 공용 토큰의 전체 한도가 소진되면 502다
   - 공용 사용량 4,999회에서 마지막 1회는 허용하고, 5,000회 뒤에는 GitHub에 보내지 않고 502 에러를 반환한다
9. 같은 저장소의 `refresh=true`는 1분에 10번까지다
   - 10번째까지 허용하고 11번째는 GitHub를 호출하지 않고 429 에러를 반환한다. 다른 저장소의 횟수와는 따로 센다
10. 모든 GitHub 호출은 공통 fetcher를 거친다
    - 동시 10개·초당 5회 제한을 여러 인스턴스가 함께 쓰며 304에도 적용한다. `Retry-After`·잔여량·초기화 시각과 403·429를 반영해 재시도한다
11. 조건부 GET으로 재검증한다
    - ETag가 있으면 `If-None-Match`, ETag 없이 Last-Modified만 있으면 `If-Modified-Since`를 보내고, 둘 다 없으면 일반 GET을 보낸다. 인증 정보는 항상 보낸다
    - 304면 저장한 본문으로 200 응답을 만들고 유효기간을 갱신한다. 오류는 캐시에 저장하지 않고 유효기간도 늘리지 않는다
12. 캐시는 1,000행까지 보관한다
    - 조회할 때마다 마지막 조회 시각을 갱신하고, 1,001번째 행이 들어오면 마지막 조회가 가장 오래된 행을 교체한다
13. 등록된 저장소와 올바른 쿼리만 처리한다
    - 등록되지 않은 `url`, 필수 값 누락, `true`·`false`가 아닌 `refresh`는 400 에러를 반환하고 GitHub를 호출하지 않는다
    - 원문 URL·브랜치명을 다시 디코딩하거나 이중 인코딩하지 않고, GitHub 요청 형식에 맞게 인코딩한다
14. 그룹 상태와 관계없이 조회할 수 있다
    - 중단·종료 그룹에서도 열람 권한이 있으면 200 응답을 반환한다
15. 공개 범위에 따라 조회할 수 있는 회원이 정해진다
    - 비공개는 그룹원, 운영진 공개는 운영진, 회원 공개는 교류 회원을 제외한 회원, 완전 공개는 모든 로그인 회원이 조회할 수 있다
    - 범위 밖 회원이면 403, 인증되지 않으면 401, 그룹이 없으면 404 에러를 반환하며 GitHub를 호출하지 않는다
16. 조건이 다른 캐시는 섞지 않는다
    - 다른 저장소·브랜치·인증 범위의 본문이나 검증자를 섞어 쓰지 않는다
