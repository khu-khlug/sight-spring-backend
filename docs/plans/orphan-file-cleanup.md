# 고아 파일 주기적 청소 설계

주기적 청소는 일회성 업로드 확인이 실행되지 않았거나 파일 삭제가 실패해 남은 데이터를 정리하는 안전망이다. 정상적인 업로드 확인은 링크 발급 서비스가 등록하는 일회성 작업이 담당한다. 공통 업로드·삭제 계약은 [그룹 API 공통 사항](group/global.md#파일-업로드와-삭제)을 따른다.

## 책임

- 링크 발급 서비스는 `file_upload.upload_check_at`을 저장하고 해당 시각에 일회성 확인을 예약한다. 발급 트랜잭션이 롤백되면 예약을 취소한다. 기록 첨부는 기록 전용 서비스, 활동보고 등 제출형 업로드는 공통 발급 서비스가 확인한다.
- 주기적 청소는 저장된 예정 시각이 지난 파일과 삭제 표시 후 남은 파일을 조회하고, 각 도메인의 판단 함수를 호출해 유효하지 않은 참조를 정리한다.
- 각 도메인은 자신의 정보로 정리 대상을 판단한다. 부가 행이 있는 도메인은 공통 참조를 해제하기 전에 해당 행을 지우는 별도 함수를 제공한다. 일회성 확인 함수와 주기적 판단·부가 행 해제 함수는 구분한다.
- 공통 청소기는 참조 정리 순서, 마지막 참조 검사, 삭제 표시와 R2 삭제를 담당하며 기능별 테이블을 직접 조회하거나 삭제하지 않는다.

## 판단 함수 등록

판단 책임을 서비스에 두고 빌드 시 등록하는 근거는 [주기적 파일 청소의 판단 함수 등록 결정](../decisions/periodic-file-cleanup.md)을 따른다.

판단 함수에는 `@PeriodicFileCleanup`과 담당 `FileReferenceType`을 지정한다. 함수 형식은 `(FileCleanupContext) -> Boolean`이며 true는 해당 참조가 정리 대상이라는 뜻이다. 입력에는 업로드 기록, 공통 참조와 R2 객체 존재 여부가 포함된다. 객체 확인이 필요하지 않아 생략한 경우 존재 여부는 null이다. 판단 함수는 데이터를 변경하지 않는다.

부가 행 해제 함수는 같은 서비스에 `@BeforePeriodicFileCleanup`을 붙여 같은 참조 종류로 선언한다. 함수 형식은 `(FileReference) -> Unit`이며, 호출자의 파일 행 잠금 트랜잭션에서 자신의 부가 행만 해제한다. 공통 참조와 업로드 기록은 공통 청소기가 처리한다.

KSP가 빌드 시 어노테이션을 읽고 `GeneratedFileCleanupRegistry`를 생성한다. 생성된 빈은 서비스들을 생성자 주입받고 `service::판단함수`와 `service::부가행해제함수` 참조로 불변 목록을 구성한다. 런타임에 어노테이션을 탐색하거나 공유 배열에 함수를 추가하지 않는다.

빌드는 함수 형식, 같은 참조 종류의 중복 판단 함수, 판단 함수와 부가 행 해제 함수의 서비스·참조 종류 불일치를 검사한다. 실제 서비스 빈의 생성과 주입은 Spring이 시작 시 확인한다. 컨텍스트 테스트는 실제 생성된 등록 코드를 사용해 필요한 종류의 등록과 호출 연결을 확인한다.

## 도메인별 판단

| 참조 종류 | 정리 대상 | 유지 대상 |
| :-- | :-- | :-- |
| 기록 첨부 | 업로드 미완료이고 객체가 없거나, 참조 개체인 기록의 행이 실제로 없음 | 소프트 삭제되어 복구 가능한 기록을 포함한 유효한 참조 |
| 기록 임시저장 첨부 | 업로드 미완료이고 객체가 없거나, 참조 개체인 임시저장이 없음 | 존재하는 임시저장의 유효한 참조 |
| 활동보고 | 참조 개체인 활동보고가 없음 | 존재하는 활동보고의 참조 |

아직 판단 함수를 등록하지 않은 참조 종류는 사용 중인 것으로 보호한다. 카드 커버의 판단 함수는 카드 커버 기능을 구현할 때 함께 등록한다. 업로드가 확인된 파일은 R2 객체가 없다는 이유만으로 참조를 해제하지 않는다. `GroupFile`은 그룹 소속·권한 메타데이터이므로 사용 참조로 세지 않는다.

## 실행 조건과 주기

- `FILE_UPLOAD_MAINTENANCE_ENABLED`의 기본값은 false이며 월간 청소만 제어한다. 일회성 확인과 요청에 따른 파일 삭제는 이 설정과 관계없이 동작한다.
- 실행 시각은 매월 1일 03:00 KST다. MySQL 연결 단위 잠금으로 여러 서버의 중복 실행을 막는다.
- 업로드 기록의 `upload_check_at`과 `(upload_check_at, id)` 인덱스를 사용한다. 1분 간격의 예약 복구나 시작 시 일회성 예약 재등록은 하지 않는다.
- DB 마이그레이션 SQL과 기존 데이터 전환 절차는 별도 범위다.

## 처리 흐름

1. 삭제 표시가 있거나 예정 시각이 지난 업로드를 아이디 커서 기준으로 나누어 조회한다.
2. 미완료 파일에 참조가 있으면 트랜잭션 밖에서 R2 객체 존재 여부를 확인한다. `NoSuchKey`만 객체 없음으로 처리한다. 그 밖의 확인 실패에서는 참조를 삭제하지 않는다.
3. 파일 행을 잠근 뒤 최신 상태와 예정 시각을 다시 확인한다. 참조도 커서로 나누어 읽고, 등록된 판단 함수에 전달한다.
4. 정리 대상인 참조에 대해서만 부가 행 해제 함수를 호출한 뒤 공통 참조를 삭제한다. 판단·해제 중 실패하면 해당 파일의 DB 변경을 롤백한다.
5. 유효한 참조나 미등록 종류의 참조가 남으면 파일을 유지한다. 참조가 없고 삭제 표시도 없을 때만 조건부 갱신으로 삭제 표시를 남긴다.
6. 커밋 후 공통 삭제 서비스에서 참조 부재를 다시 확인하고 R2 객체를 삭제한다. 성공 또는 `NoSuchKey`이면 `GroupFile` 메타데이터와 업로드 기록을 삭제한다.

## 실패 처리와 기록

- 파일 하나씩 독립적으로 처리하며, 대상과 참조를 한 번에 모두 메모리에 올리지 않는다.
- 월간 청소의 R2 확인과 삭제는 DB 트랜잭션 밖에서 실행한다. 일회성 확인과 월간 청소가 겹치면 파일 행 잠금과 최신 상태 검사로 보호한다.
- `NoSuchBucket`·인증 실패처럼 설정 문제인 오류에서는 남은 월간 처리를 중단한다. 개별 일시적 오류는 해당 파일을 남기고 다음 파일을 처리한다.
- 실행마다 시작·종료 시각과 삭제 성공·객체 없음·실패·건너뜀 건수를 기록한다. 개별 실패에는 업로드 아이디와 파일 키를 남긴다.
- 삭제 표시 후 두 달 이상 남은 업로드는 장기 미삭제 경고를 기록한다.

## 범위 밖

- 기존 `khlug_files`와 레거시 객체는 신규 업로드 청소 대상이 아니다. [제공 전환](file-migration.md)을 따른다.
- DB 업로드 기록 없이 R2에만 남은 객체는 찾지 않는다.
- 기록 본문을 파싱하지 않는다. 첨부 연결 목록을 기준으로 판단한다.
