# 고아 파일 주기적 청소 설계

R2에 남아 있지만 아무 데이터도 참조하지 않는 고아 파일과 그에 대응하는 업로드 기록, 삭제 표시 후 R2 삭제에 실패해 남은 업로드 기록을 주기적으로 정리한다. 업로드·삭제 흐름은 [그룹 API 공통 사항의 파일 업로드와 삭제](group/global.md#파일-업로드와-삭제)를 따른다.

파일 정리는 그때그때 처리하는 것이 원칙이다. 파일 삭제는 요청을 처리할 때 바로 하고, 업로드되지 않은 업로드 기록은 링크 발급 때 등록한 업로드 확인 예약이 정리한다. 이 청소는 그 과정에서 빠진 것(R2 삭제 실패, 서버 재시작으로 사라진 예약, 업로드했지만 제출하지 않은 파일 등)을 처리하는 안전망이다.

## 전제

- 업로드 기록 하나는 R2 객체 하나와 1:1로 대응하며 DB가 파일 상태의 기준이다.
- 업로드 기록에는 삭제 표시와 그 시각을 남길 수 있어야 한다. 삭제 표시가 없으면 유효한 파일이다.
- 사용자 요청 처리 중의 파일 삭제는 삭제 표시 → 커밋 후 R2 삭제 → 성공 시 업로드 기록 삭제 순서로 처리하며, R2 삭제에 실패한 기록은 이 청소가 다시 처리한다.

## 실행 주기

- 실행 시각은 [그룹 API 공통 사항의 파일 청소 기준](group/global.md#파일-청소-기준)을 따른다.
- 같은 청소가 동시에 두 번 실행되지 않아야 한다. 서버가 여러 대이거나 이전 실행이 끝나지 않은 경우에도 한 번에 하나만 실행되도록 잠금을 둔다.

## 청소 대상

### 1. 삭제 표시 후 남은 업로드 기록

- 조건: 삭제 표시가 있는 업로드 기록
- 사용자 요청 중 R2 삭제가 실패했거나 커밋 후 삭제 단계 전에 서버가 중단된 경우다.
- 처리: R2 객체 삭제 → 성공 또는 `NoSuchKey`이면 업로드 기록 삭제.

### 2. 사용하지 않은 업로드

- 조건: 삭제 표시가 없고, 업로드 확인 예약 시각이 지났으며, 아래 중 하나에 해당하는 업로드 기록. 기준은 [그룹 API 공통 사항의 파일 청소 기준](group/global.md#파일-청소-기준)을 따른다.
  - 활동보고·카드 커버 업로드 기록: 사용되지 않음
  - 기록 첨부 업로드 기록: 연결 행이 하나도 없음
- 업로드 확인 예약이 실행되지 않았거나, 업로드는 됐지만 제출 요청이 실패했거나, 연결 해제 후 삭제 단계 전에 서버가 중단된 업로드다.
- 처리: 먼저 삭제 표시를 남긴 뒤 1번과 같은 방식으로 삭제한다.
- 삭제 표시는 "아직 사용되지 않았거나 연결 행이 없고, 삭제 표시가 없을 때만" 남기는 조건부 갱신으로 한다. 그 사이 사용되거나 연결된 기록은 갱신되지 않으므로 지우지 않는다.

## 처리 규칙

- 업로드 기록 하나씩 독립적으로 처리한다. 하나의 실패가 다른 기록의 처리를 막지 않는다.
- 대상은 일정 개수씩 나눠 조회·처리한다. 한 번에 전체를 메모리에 올리지 않는다.
- 업로드 기록 삭제와 삭제 표시는 기록마다 짧은 트랜잭션으로 처리한다. R2 호출을 트랜잭션 안에 두지 않는다.
- `NoSuchKey`는 삭제 성공으로 처리한다. 같은 기록을 여러 번 처리해도 결과가 같아야 한다.
- `NoSuchBucket`이나 인증 실패처럼 설정 문제로 보이는 오류가 나면 남은 처리를 멈추고 오류로 기록한다. 같은 오류를 모든 기록에서 반복하지 않는다.
- 그 밖의 개별 실패(5xx, 네트워크 오류)는 해당 기록을 남겨 두고 다음 기록으로 넘어간다. 다음 실행에서 다시 시도한다.
- 사용 중(활동보고·카드 커버는 사용 처리됨, 기록 첨부는 연결 행이 있음)이고 삭제 표시가 없는 파일은 어떤 경우에도 청소 대상이 아니다.

## 기록과 감시

- 실행마다 시작·종료 시각, 대상별 처리 건수(성공, `NoSuchKey`, 실패)를 로그로 남긴다.
- 실패한 기록은 업로드 기록 아이디·파일 키·오류 종류를 로그로 남긴다.
- 삭제 표시 후 오래 남은 기록(예: 두 번의 실행 주기 이상)이 있으면 반복 실패로 보고 경보 대상으로 삼는다.

## 범위 밖

- DB에 업로드 기록 없이 R2에만 남은 객체는 찾지 않는다. 업로드 링크 발급이 기록을 먼저 만들기 때문에 정상 흐름에서는 생기지 않는다.
- 삭제된 카드·기록처럼 복구 가능한 데이터의 첨부 파일은 연결 행이 남아 있으므로 데이터가 영구 삭제될 때까지 사용 중인 파일로 본다.
- 기록 본문과 연결 목록이 어긋난 경우(연결은 있지만 본문에 보이지 않는 파일)는 찾지 않는다. 서버는 기록 본문을 파싱하지 않으며, 연결 목록을 첨부 파일의 기준으로 본다.
