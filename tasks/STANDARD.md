# Backend Task 문서 작성 Standard

## 목적

Backend Task 문서는 구현 방법을 지시하는 문서가 아니다. 작업으로 인해 달라지는 계약, 비즈니스 동작, 비가역적 결정을 사람이 구현 전에 검토할 수 있도록 설명하는 문서다.

사람은 다음 내용을 검토한다.

- 외부 소비자와 맺는 계약
- 데이터베이스와 맺는 계약
- 외부 시스템과 맺는 계약
- 사용자에게 관찰되는 비즈니스 동작
- 보안, 개인정보 및 비가역적 부작용
- 호환성 및 배포 전략

내부 구현은 이 문서와 `rules/`의 규칙을 만족하는 범위에서 구현자가 결정한다. 반복되는 구현 문제가 발견되면 개별 Task 문서에 구현 방법을 추가하기보다 `rules/`를 보강하고, 기계적으로 확인할 수 있는 규칙은 lint로 옮긴다.

## 저장 위치와 상태

- 완료되지 않은 Task 문서는 `tasks/open/`에 둔다.
- 완료된 Task 문서는 `tasks/completed/`로 옮긴다.
- `tasks/STANDARD.md`는 작성 원칙을 정의한다.
- `tasks/TEMPLATE.md`는 필수 섹션과 순서를 정의한다.

## 작성 원칙

### 구현이 아니라 동작을 설명한다

Task 문서는 클래스, 메서드, 내부 호출 순서를 중심으로 작성하지 않는다. 구현 전에는 존재하지 않을 수 있고 구현 중에 바뀔 수 있는 identifier에 문서가 종속되기 때문이다.

대신 도메인 용어를 사용해 다음을 설명한다.

- 누가 무엇을 요청하거나 수행하는가
- 어떤 조건에서 동작이 허용되거나 거부되는가
- 어떤 상태가 어떻게 바뀌는가
- 어떤 데이터가 저장되거나 외부로 전달되는가
- 성공과 실패를 외부에서 어떻게 관찰하는가

내부 identifier를 사용해야만 의미가 명확해지는 경우를 제외하면 클래스명, 메서드명, 변수명은 작성하지 않는다. 특정 identifier가 HTTP field, database schema, configuration key, event field 등 계약의 일부라면 정확한 이름을 작성한다.

### 저장소가 사용하는 언어를 사용한다

비즈니스에서 합의한 유비쿼터스 언어를 사용한다. 같은 개념을 문서마다 다른 단어로 바꾸어 쓰지 않는다.

일반적인 기술 용어, 비즈니스 용어, 저장소에서 이미 영어로 사용하는 용어는 억지로 번역하지 않는다. 번역으로 인해 기존 용어와의 대응 관계를 다시 추론해야 하는 표현을 피한다.

문장은 특정 구현을 읽지 않아도 의미와 다음 동작을 예측할 수 있도록 작성한다.

### 변경과 유지를 모두 명시한다

모든 필수 영역에는 변경 내용을 작성하거나 `변경 없음`을 명시한다. 섹션을 생략하거나 빈 상태로 두지 않는다.

기존 계약을 유지해야 한다면 단순히 `변경 없음`으로 끝내지 않고, 작업 중 실수로 달라질 가능성이 높은 항목을 유지 조건에 작성한다.

예:

```markdown
## HTTP API 계약

변경 없음

### 유지 조건

- 가입 신청이 존재하지 않을 때의 `404 Not Found` 응답을 유지한다.
```

### 결정되지 않은 내용을 숨기지 않는다

구현 전에 사람의 결정이 필요한 내용은 임의로 가정하지 않는다. `사람의 결정 필요` 섹션에 선택지, 영향, 권장안을 작성한다.

구현자가 자유롭게 정해도 되는 세부사항은 의사결정 항목으로 올리지 않는다.

## 필수 섹션

모든 Task 문서는 아래 섹션을 같은 이름과 순서로 작성한다.

### 1. 작업 개요

작업의 목적과 완료 후 달라지는 결과를 짧게 설명한다. 구현 파일이나 구현 순서를 나열하지 않는다.

반드시 포함할 내용:

- 해결하려는 문제 또는 제공하려는 기능
- 작업의 대상 사용자 또는 시스템
- 완료 여부를 판단할 수 있는 결과

### 2. 비즈니스 동작

사용자 또는 외부 시스템이 관찰할 수 있는 전체 흐름과 비즈니스 규칙을 도메인 용어로 설명한다.

반드시 포함할 내용:

- 동작의 시작 조건
- 주요 상태와 상태 전이
- 허용 및 거부 조건
- 성공했을 때 발생하는 결과
- 실패했을 때 발생하는 결과
- 중복 요청 또는 재시도 시의 동작

세부 알고리즘, 내부 객체 사이의 호출 순서, 클래스명과 메서드명은 작성하지 않는다.

변경이 없다면 `변경 없음`을 작성한다.

### 3. HTTP API 계약

새로 추가하거나 변경하는 모든 HTTP API를 작성한다.

API마다 반드시 포함할 내용:

- HTTP method와 path
- 인증 및 인가 조건
- path, query, header, cookie parameter
- request body
- response status와 body
- error status와 외부에서 구분 가능한 error
- 각 field의 이름, 타입, 필수 여부, nullable 여부 및 의미
- pagination, filtering, sorting 규칙
- 멱등성 및 중복 요청 처리
- 기존 API와의 호환성

해당하지 않거나 변경이 없다면 `변경 없음`을 작성한다.

### 4. 데이터베이스 계약

데이터베이스 schema와 저장되는 데이터의 의미에 대한 변경을 작성한다.

반드시 포함할 내용:

- 추가, 변경, 삭제하는 table과 column
- type, 길이 또는 precision
- nullable 여부와 default
- primary key, foreign key, unique 및 check constraint
- index
- enum 등 제한된 저장값과 각 값의 의미
- 연관관계와 삭제 정책
- 기존 데이터에 적용할 migration 또는 backfill
- 대략적인 대상 데이터 규모와 lock 또는 성능 위험
- 구버전과 신버전 애플리케이션의 동시 실행 호환성
- rollback 가능 여부와 방법

JPA entity의 내부 메서드나 entity class 이름 자체는 계약이 아니다. 실제 schema, 저장값 또는 데이터 의미에 영향을 줄 때만 작성한다.

해당하지 않거나 변경이 없다면 `변경 없음`을 작성한다.

### 5. 외부 시스템 계약

다른 서비스, Discord, webhook consumer, message consumer 등 저장소 밖의 시스템과 주고받는 계약을 작성한다.

외부 연동마다 반드시 포함할 내용:

- 대상 시스템과 연동 목적
- 요청, 응답, event 또는 message payload
- 인증 방식과 필요한 권한
- timeout, retry 및 rate limit 처리
- 중복 전달과 재처리 시의 동작
- 부분 실패 시의 동작
- 기존 consumer 또는 provider와의 호환성

해당하지 않거나 변경이 없다면 `변경 없음`을 작성한다.

### 6. 보안 및 개인정보

접근 권한과 민감한 데이터 처리의 변경을 작성한다.

반드시 포함할 내용:

- 인증 및 인가 범위
- 새로 수집, 저장, 반환 또는 전달하는 개인정보와 민감정보
- log, metric, tracing에 포함될 수 있는 민감정보
- 데이터 보존 및 삭제 조건
- 권한 상승 또는 정보 노출 가능성

해당하지 않거나 변경이 없다면 `변경 없음`을 작성한다.

### 7. 비가역적 부작용 및 운영 영향

실행 후 되돌리기 어렵거나 운영 환경에 영향을 주는 동작을 작성한다.

반드시 포함할 내용:

- 데이터 삭제 또는 대량 변경
- 외부 알림과 message 발송
- 비용을 발생시키는 외부 호출
- batch와 scheduler의 실행 조건
- 예상 호출량 또는 처리량 변화
- 장애 시 중단, 재개 및 복구 방법
- observability에 필요한 log, metric 또는 alert

해당하지 않거나 변경이 없다면 `변경 없음`을 작성한다.

### 8. 호환성 및 배포

계약 변경을 안전하게 적용하는 순서와 전환 방법을 작성한다.

반드시 포함할 내용:

- 하위 호환 여부
- 함께 변경되어야 하는 consumer
- 단계적 배포 또는 feature flag 필요 여부
- migration, backfill, application 배포 순서
- 구버전과 신버전이 함께 실행되는 동안의 동작
- rollback 조건과 제한

호환성 또는 배포상 고려사항이 없다면 `변경 없음`을 작성한다.

### 9. 검증

구현이 계약과 비즈니스 동작을 만족하는지 검증하는 방법을 작성한다.

반드시 포함할 내용:

- 주요 성공 흐름
- 주요 실패 흐름
- 권한 검증
- 경계값 및 상태 전이
- 중복 요청과 재시도
- migration 및 기존 데이터 검증
- 외부 시스템 실패 검증

해당하지 않는 항목은 제외할 수 있지만 검증 섹션 자체는 생략할 수 없다.

### 10. 사람의 결정 필요

구현 전에 사람이 결정하거나 승인해야 하는 내용을 작성한다.

각 항목에 반드시 포함할 내용:

- 결정할 질문
- 가능한 선택지
- 각 선택지의 계약, 운영 및 호환성 영향
- 권장안과 그 이유

결정할 내용이 없다면 `없음`을 작성한다.

### 11. 구현자 재량

계약과 동작에 영향을 주지 않아 구현자가 자유롭게 정할 수 있는 내용을 작성한다.

일반적으로 다음은 구현자 재량이다.

- 내부 class, method 및 variable 이름
- private 함수 분리
- 내부 제어 흐름
- 동일한 결과를 만드는 query 또는 mapping 구현
- 보조 타입과 파일 구성
- `rules/`가 허용하는 범위의 library 활용

다음 identifier는 외부에서 관찰되거나 runtime 동작에 사용될 수 있으므로 구현자 재량으로 간주하지 않는다.

- HTTP 및 serialization field 이름
- table, column, index 및 constraint 이름
- event와 message field 이름
- configuration key와 environment variable 이름
- 명시적인 이름으로 조회되는 Spring bean
- metric, log field 및 tracing attribute 이름
- 저장소 밖에서 참조하는 공개 identifier

별도로 제한할 내용이 없다면 `추가 제한 없음`을 작성한다.

### 12. 비목표

이번 작업에서 의도적으로 다루지 않는 인접 영역을 작성한다. 작업 범위가 구현 중 암묵적으로 확장되는 것을 막기 위한 섹션이다.

비목표가 없다면 `없음`을 작성한다.

## 사람의 검토가 필요한 변경

다음 중 하나라도 해당하면 구현 전에 사람의 검토를 받아야 한다.

- HTTP API 계약의 추가, 변경 또는 삭제
- 인증 또는 인가 조건 변경
- database schema, constraint, index 또는 저장값 의미 변경
- migration 또는 backfill 실행
- 외부 시스템과의 계약 변경
- 사용자에게 관찰되는 비즈니스 흐름 또는 규칙 변경
- 개인정보 또는 민감정보 처리 변경
- 데이터 삭제, 대량 변경, 외부 발송 등 비가역적 부작용 추가
- 호환되지 않는 변경
- 구현자가 안전하게 결정할 수 없는 요구사항의 모호함

내부 구현 방식만 달라지고 위 항목에 해당하지 않는다면 별도의 사람 승인을 요구하지 않는다.

## `rules/`, Task 문서 및 lint의 역할

- Task 문서는 이번 작업의 계약, 비즈니스 의미와 승인 경계를 기록한다.
- `rules/`는 여러 작업에서 반복 적용할 구현 가드레일을 정의한다.
- lint는 필수 내용의 존재와 문서 형식을 deterministic하게 검사한다.
- 사람은 Task 문서에 드러난 계약과 결정을 검토한다.

문제가 반복될 가능성이 있고 명확한 규칙으로 일반화할 수 있다면 `rules/`를 보강한다. 기계적으로 판별할 수 있다면 lint를 추가한다. 특정 작업에만 해당하는 제품 결정은 Task 문서에 남긴다.

lint는 설계의 타당성을 판단하지 않는다. 예를 들어 database 변경을 감지했을 때 `데이터베이스 계약`과 migration 설명이 존재하는지는 검사할 수 있지만, 선택한 schema가 최선인지는 판단하지 않는다.

현재 lint는 `tasks/open/`과 `tasks/completed/`의 Markdown 문서에 대해 다음 내용만 검사한다.

- `tasks/TEMPLATE.md`에 정의된 모든 `##` 섹션이 정확히 한 번 존재한다.
- 필수 섹션끼리의 상대적 순서가 Template과 같다.
- 각 필수 섹션에 공백을 제외한 내용이 한 글자 이상 존재한다.

추가 `##` 섹션은 허용한다.

## 작성 예시

```markdown
# 가입 신청 검토 시각 기록

## 작업 개요

운영진이 가입 신청을 승인하거나 거절한 시각을 기록해 이후 검토 이력을 확인할 수 있게 한다.

## 비즈니스 동작

- 대기 중인 가입 신청을 운영진이 승인하거나 거절하면 검토 시각을 기록한다.
- 이미 처리된 가입 신청을 다시 처리할 수 없다.
- 검토 시각 기록 실패 시 가입 신청의 상태도 변경하지 않는다.

## HTTP API 계약

변경 없음

### 유지 조건

- 기존 승인 및 거절 API의 method, path, request와 response를 유지한다.
- 운영진만 가입 신청을 승인하거나 거절할 수 있다.

## 데이터베이스 계약

- 가입 신청에 검토 시각을 나타내는 nullable timestamp column을 추가한다.
- 기존 가입 신청의 검토 시각은 `null`로 유지한다.
- 신규 column 추가와 application 배포는 구버전 application과 호환된다.
- column 제거 없이 application만 rollback할 수 있다.

## 외부 시스템 계약

변경 없음

## 보안 및 개인정보

변경 없음

## 비가역적 부작용 및 운영 영향

변경 없음

## 호환성 및 배포

1. nullable column을 먼저 추가한다.
2. 신규 application을 배포한다.

## 검증

- 대기 중인 가입 신청을 승인하면 상태와 검토 시각이 함께 저장된다.
- 대기 중인 가입 신청을 거절하면 상태와 검토 시각이 함께 저장된다.
- 처리할 수 없는 가입 신청은 상태와 검토 시각이 모두 유지된다.
- 기존 데이터의 검토 시각은 migration 후에도 `null`이다.
```
